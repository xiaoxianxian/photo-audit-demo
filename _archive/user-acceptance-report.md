# Photo Audit Demo -- 普通用户（审核员）验收报告

## 一、验收概况

- **验收角色：** 普通审核员（日常使用审核工作台审核图片/视频内容的一线操作人员）
- **验收方式：** 代码审查（无法实际运行，仅通过源码审阅）
- **验收日期：** 2026-06-27
- **验收范围：** 登录/注册、业务看板、审核工作台、申诉管理、直播电视墙 五个模块

---

## 二、逐项验收结果

### 1. 登录/注册页面

**评级：-- 需改进**

#### 优点

- **暗黑主题一致性：** Login.tsx 和 Register.tsx 均使用 `#0a0a0a` 深色背景 + `#141414` 卡片色，与整体应用风格统一，视觉上没有割裂感。
- **表单字段合理：** 登录只需用户名+密码，注册多了 display_name、邮箱（可选）、确认密码，字段齐全，符合 B 端平台注册流程。
- **注册页面确认密码校验写法规范：** Register.tsx 使用了 Ant Design `dependencies` + 自定义 validator 来比对两次密码，写法正确（评审报告中前端工程师已标记为优点）。
- **注册链接已修复：** Login.tsx 第 111 行使用的是 `<Link to="/register">`，不再是评审报告中指出的 `<a href="#register">` bug，说明该问题已修复。
- **防重复提交：** 登录和注册按钮都有 `loading` 状态，防止用户连续点击。

#### 问题

- **[P2] 登录成功后 user 信息提取路径含糊：** Login.tsx 第 22-26 行，`result.user?.id` / `result.user?.role` / `result.user?.tenant_id` 都是可选链，如果后端返回字段名不匹配（比如返回的是 `user_id` 而非 `id`），userInfo 的所有字段都会拿到空字符串，导致登录后很多功能异常但没有明显提示。建议在 catch 之外增加 `if (!userInfo.id)` 的空值检查。
- **[P2] 注册自动登录后 username 可能丢失：** Register.tsx 第 31 行 `username: values.username` 是硬编码填入的，不依赖后端返回。但如果后端注册接口返回的结构变化，`result.user?.id` 为空的话，用户实际上是以"无名氏"身份登录的，侧边栏显示"审核员"这个名字只是 Layout.tsx 第 43 行的 fallback。
- **[P2] 没有忘记密码/找回功能：** 登录页面没有任何找回密码入口，对于 B 端平台来说不太友好。

### 2. 业务看板（Dashboard）

**评级：-- 需改进**

#### 优点

- **统计数据卡片展示清晰：** DashboardStatsCard 组件用 Row/Col 栅格布局展示了今日已审、通过率、驳回率、平均风险分、待审元素、分歧数六个指标，每个都配了后缀和单位，一目了然。
- **审核员绩效表真实：** ReviewerPerformanceTable 已对接真实 DB 查询（ReviewService.GetReviewerPerformance），不再是空返回（第六批开发已修复）。
- **租户/团队 Tab 切换逻辑干净：** 使用 `activeTab` state 控制，数据各自独立 fetch，没有耦合。
- **Modals 组件化：** TenantModal 和 TeamModal 封装良好，表单校验通过 `validateFields()` 统一处理，打开时 `setFieldsValue` 回显数据，关闭时重置。
- **删除操作有二次确认：** TenantTable 中删除按钮外面包了一层 `Popconfirm`，避免了误删。

#### 问题

- **[P1] "今天已审"单位和文案不当：** Dashboard.tsx 第 378 行显示 `今日已审  {stats.today_reviewed} 张`，后缀用的是"张"，但这个数据来自 `countApprovalsAndRejections`，后端统计的是 `audit_records` 行数（即元素级别的审核次数），不是"张图"。一个视频可能有 10 个元素，被审核 10 次，这里的"张"会造成误导。应改为"条"或"次"。
- **[P1] 绩效表列宽没有设置：** ReviewerPerformanceTable 没有为各列指定 `width`，当审核员名字较长时，"操作"列可能被挤出去或者表格横向溢出。建议在 columns 中给 `reviewer_name` 加 `width: 120`，给 `id` 类窄列加 `width: 100`。
- **[P2] leaders（负责人列表）数据来源可疑：** Dashboard.tsx 第 459-462 行，`leaders`  useMemo 只包含当前登录用户自己：`[{ id: currentUser?.id, ... }]`。这意味着新建团队时，负责人下拉框里永远只有自己一个人。应该调用后端用户列表 API 来获取当前租户下的所有用户作为负责人选项。
- **[P2] 缺少行动号召/待办提醒：** 评审报告指出 Dashboard 缺少待办提醒。目前看板只展示统计数字，没有告诉审核员"你还有 XX 个待审元素需要处理"。建议在 pending_elements 旁边加一个"去审核"的快速跳转按钮。
- **[P2] 统计数据无 loading 骨架屏：** 虽然用了 `loading={statsLoading}` 控制 `DashboardStatsCard.loading`，但 Ant Design Card 的 loading 只是一个灰色占位闪烁，信息量为零。对于真实使用场景，建议加 Skeleton 骨架屏让用户知道数据正在加载。

### 3. 审核工作台（Review）

**评级：-- 需改进**

#### 优点

- **卡片设计直观：** ElementCard 组件展示了元素类型标签、风险分 Badge、AI 状态 Tag、风险类型 Tag、置信度，信息密度适中，不凌乱。
- **裁判分歧高亮已实现：** Review.tsx 第 109 行 `element.is_conflict ? '2px solid #fa8c16' : '1px solid #2a2a2a'`，分歧元素橙色边框 + 第 119-125 行的"分歧"Tag + Tooltip，视觉信号清晰，符合评审报告中产品经理的期望。
- **风险分四级颜色方案合理：** riskColor() 函数（第 57-62 行）用绿/黄/橙/红四个颜色对应 0-20/20-60/60-80/80+ 四个区间，审核员一眼就能判断风险级别。
- **筛选器已对接后端：** fetchElements（第 245-265 行）的 useCallback 依赖数组包含了 `filterStatus`、`filterType`、`riskRange`，筛选条件变化时会触发后端重新查询。此前评审报告中指出的"前端 filter 不调后端 API"问题已修复。
- **打回操作有二次确认：** 第 193-207 行使用了 Ant Design 的 `Popconfirm`，点击打回按钮会先弹确认框，不会再误触。
- **图片预览不可用时回退：** 第 147-149 行，`onError` 事件处理隐藏了 img 并显示"预览不可用"文字。
- **分页组件健全：** 上下页按钮根据 page 和 total 正确 disable，页码显示"第 X / Y 页"。
- **key 使用正确：** Row/Col 中 `key={element.id}` 使用了唯一的元素 ID，不会触发 React key 警告。
- **没有 as any 类型断言：** content-api.ts 中之前评审指出的多处 `as any` 已全部移除，改用泛型 `ApiPaginatedResponse<T>`。

#### 问题

- **[P1] 风险分排序器缺失：** 筛选区域只有元素类型下拉框、AI 状态下拉框和风险分滑块，没有排序下拉框。评审报告中产品经理指出"风险分排序最重要（高风险优先）"，但目前 Review.tsx 没有任何排序 UI。虽然 content-api.ts 中 `getPendingElements` 定义了 `sort_by` 和 `sort_order` 参数，但 Review.tsx 没有传入这些参数，后端排序能力没有被利用。
- **[P1] 统计标签展示的是前端内存数据：** Review.tsx 第 347-349 行，"已通过"、"已打回"、"分歧" 的计数是基于 `elements.filter(...)` 在**当前页 20 条数据**上计算的，不是后端的总计数。翻页后这些数字会随着当前页数据变化而变化，误导审核员认为总数很少。应改为在统计数据中从后端获取全局计数。
- **[P2] 打回原因选择交互不够直观：** 第 211-225 行，用户确认 Popconfirm 后才出现 Select，但 Select 一旦选择标签就自动提交。建议改为 Select 展开后，用户选择好标签再点"确定"按钮才提交，这样用户可以反复调整选择。当前的 `onChange` 里"选择一个就提交"的流程不够友好。
- **[P2] 图片预览太小（120px）且无放大功能：** 第 132 行图片预览区域固定 `height: 120`，审核一张图要放大看不清楚细节。评审报告指出应支持 Image.PreviewGroup 放大查看。目前没有这个功能。
- **[P2] 无键盘快捷键支持：** 审核员一天要看几百张图，目前只能通过鼠标点击卡片上的按钮。没有左右方向键切换卡片、Enter 快速通过等快捷键。
- **[P2] 无批量审核交互：** 虽然有 `batchReview` API（content-api.ts 第 145-160 行），但 Review.tsx 卡片上没有 checkbox，也没有批量操作栏。
- **[P2] 缺少"上一个/下一个"导航：** 审核完一张图后，需要滚动找下一张，没有分页内导航按钮。
- **[P1] filterType 空字符串问题：** Review.tsx 第 306 行 `onChange={(val) => setFilterType(val || '')}`，当用户点击"清空"时，Select 的 value 会变成 `undefined`，被转换为空字符串 `''`。然后在 fetchElements 第 250 行 `element_kind: filterType || undefined` 又转回 `undefined`。虽然最终效果是对的，但这绕了一圈，直接用 `setFilterType(val)` 并让 getPendingElements 过滤空串即可。
- **[P2] handleApprove/handleReject 没有乐观更新：** 调用 API 成功后才刷新整个列表（第 276-277 行），如果列表有 1000 条分页数据，刷新后当前页会跳走。建议在提交成功后，先从 `elements` 数组中移除该元素（乐观更新），失败时再加回来，提升操作流畅度。

### 4. 申诉管理（Appeal）

**评级：-- 需改进**

#### 优点

- **申诉状态标签颜色区分到位：** APPEAL_STATUS_LABELS 定义了四种状态的配色（待审核-gold、审核中-blue、已改判-green、维持原判-red），一目了然。
- **详情弹窗信息完整：** AppealDetailModal 展示申诉理由、证明材料链接、处理备注，信息层级清晰。
- **详情弹窗两条操作路径都有确认：** 评审报告指出的"[Bug] Modal 两条操作路径校验不一致"问题已修复。现在"维持原判"和"改判解封"都在 footer 中使用了 `Popconfirm`，都弹出确认框后才调用 `onResolve`。
- **列表页维护原判/改判解封快捷入口：** Appeal.tsx 第 218-237 行，表格"操作"列直接在列表中提供了快捷操作按钮，不必每次都点开详情弹窗。
- **操作前二次确认：** 列表页的两个快捷按钮都包在 Popconfirm 中，防止误操作。
- **key 使用正确：** 证据链接 map 中使用了 `key={i}`，虽然是索引但证据列表顺序通常不变，影响不大。

#### 问题

- **[P1] 申诉列表只查 submitted 状态：** Appeal.tsx 第 147 行 `getAppeals({ status: 'submitted', ... })`，只能看到待审核的申诉。评审报告中产品经理明确指出"看不到已处理记录"是一个痛点。应增加 Tab 切换（待处理 / 已处理），类似改进方案中任务 3.9 所述。
- **[P2] 申诉列表没有分页：** Table 组件设置了 `pagination={false}`（第 256 行），即使 API 支持分页（page_size=50），前端也不展示分页控件。如果申诉量大，一页会很长。
- **[P2] 证明材料链接只是文字链接：** 第 118 行 `<a href={url} target="_blank">查看附件</a>` 是纯文本链接，如果材料是图片，无法在弹窗中预览大图。建议用 Ant Design Image.PreviewGroup 或 Lightbox 展示图片材料。
- **[P2] 申诉详情弹窗中"处理备注"和"提交"耦合在一起：** 第 125-127 行备注字段 `name="comment"` 是 Form.Item 内的嵌套 name，但外层 Form 没有通过 `form` prop 暴露，所以 `name="comment"` 可能无法正确绑定。仔细看，这是一个独立的 `<Form>` 但备注字段用了 `name` 而非 `Form.Item name`，存在绑定隐患。
- **[P2] 申诉列表顶部"共 X 条申诉记录"只显示当前页数量：** 第 248 行 `appeals.length` 是当前请求到的 50 条上限，不是总申诉数。应该使用 API 返回的 total 字段。
- **[P2] 缺少申诉类型/来源筛选：** 没有按内容类型（供稿/短视频/直播）或申诉原因筛选的功能。

### 5. 直播电视墙（LiveWall）

**评级：-- 需改进**

#### 优点

- **高风险直播间可视化提醒：** StreamTile 第 60 行 `riskScore > 60 ? '2px solid #fa541c' : '1px solid #2a2a2a'`，风险高的流边框变橙色，非常醒目。
- **图片加载失败回退合理：** 第 71-73 行 onError 隐藏图片，虽然没有显示备用图但也没有白屏崩溃。
- **WebSocket 实时更新已实现：** 第 187-211 行建立了 WebSocket 连接，收到 `snapshot_update` 消息后刷新列表。
- **WebSocket 卸载防护已实现：** 第 156-162 行用 `isMounted` ref 管理组件挂载状态，第 200 行 `!cancelledRef.current` 在消息回调中检查，第 207-210 行的 cleanup 函数正确关闭 WS 连接。此前评审报告中指出的"Bug - WebSocket callback 无组件卸载防护"问题已修复。
- **自动降级轮询：** 第 214-221 行设置了 10 秒定时轮询作为 WebSocket 断开时的降级方案。
- **实时统计栏：** 在线直播间数、高风险直播间数、总观看人数三个统计，帮助审核员快速掌握全局态势。
- **高风险警告条：** 第 252-260 行，当有高风险直播间时展示 Alert 警告条，起到提醒作用。
- **key 使用正确：** 使用 `key={stream.id}`，唯一标识。

#### 问题

- **[P2] 电视墙缺少点击跳转审核的快捷入口：** StreamTile 组件第 48-142 行，点击图片或格子没有任何点击事件处理。评审报告中产品经理指出"电视墙缺少点击跳转审核快捷入口"——审核员看到高风险流时，希望能一键跳转到审核工作台对应元素进行详细审核。
- **[P2] 离线状态处理不足：** 第 75-88 行，当没有 `snapshot_url` 时只显示一个相机图标，没有明确标注"离线"或"无信号"。直播流断开时，摄像头图标容易让人误解为"还没开播"而不是"已掉线"。建议加一个"离线"文字标签。
- **[P2] StreamTile 是纯展示组件，没有 hover 交互：** 卡片上没有 hover 放大、悬停显示更多信息的效果，不如竞品电视墙的交互丰富。
- **[P2] 视频帧/直播流的分辨率未知：** 140px 高度的图片如果来自不同分辨率的直播流，`objectFit: 'cover'` 会导致图片被裁剪，看不清全貌。审核员可能需要完整的画面来判断内容。
- **[P2] 没有按风险分排序/置顶：** 高风险的流应该自动排在前面的位置，目前 grid 的顺序取决于后端 API 返回的自然顺序。

## 四、遗留问题

### 高优先级（影响日常工作流程）

1. **缺少风险分排序功能：** 审核工作台没有"风险分降序"排序选项，高风险优先是最核心的效率需求。
2. **申诉列表缺少已处理记录 Tab：** 审核员无法查看历史已处理的申诉记录，不利于追溯和复盘。
3. **统计标签数据不准确：** 审核工作台"已通过/已打回/分歧"计数仅基于当前页 20 条数据，不是全局统计。
4. **Dashboard leaders 数据来源有误：** 负责人下拉框只有自己一人，无法为团队选择正确的负责人。

### 中优先级（影响工作效率和体验）

5. **图片预览太小且无放大功能：** 120px 卡片高度看不清图片细节，缺少 Image.PreviewGroup 放大查看。
6. **无键盘快捷键支持：** 审核员期望的方向键切换、Enter 快速通过等快捷键均未实现。
7. **无批量审核交互：** API 已有 batchReview 但前端无 checkbox 多选 UI。
8. **直播电视墙无快捷审核入口：** 高风险直播流无法一键跳转到审核工作台。
9. **直播流离线标识不清：** 无截图时只显示摄像头图标，看不出是"未开播"还是"已离线"。
10. **申诉详情备注字段绑定隐患：** Form.Item 的 `name="comment"` 可能在嵌套结构中无法正确绑定。
11. **操作后无乐观更新：** 审核通过后列表完全重新请求，大列表翻页体验差。

### 低优先级（体验优化）

12. **没有"上一个/下一个"导航按钮。**
13. **Dashboard 缺少行动号召/待办提醒。**
14. **申诉列表证明材料只有文字链接，无图片预览。**
15. **审核工作台 filterType 空字符串中转冗余。**

## 五、总体评价

作为一线审核员，我对当前平台的使用感受可以概括为：**骨架搭得不错，但离"好用"还差临门一脚。**

**做得好的方面：**
- 暗黑主题贯穿所有页面，视觉统一；
- 风险分四级颜色（绿/黄/橙/红）识别效率高，看到红色就知道要先审；
- 裁判分歧元素橙色高亮边框 + Tag，视觉信号清晰，不会漏看；
- 状态机设计合理（pending -> approved/rejected/appealed），申诉流程闭环；
- 打回二次确认、WebSocket 实时更新等关键交互缺陷已修复；
- 没有 mock 数据残留，前端代码和生产环境的预期行为一致。

**最需要补齐的短板：**
1. **审核工作台缺排序和批量操作。** 我一天要看几百张图，最需要的功能是一进来就看到风险最高的在前面（排序），然后批量勾多选过。这两个功能都没有，效率大打折扣。
2. **统计数字不准。** 看板说今天过了 10 张图，但我只看了 3 张，另外 7 张可能是别人审的。这种"假数字"让我对看板失去信任。
3. **图片太小看不清。** 120px 的高度，缩略图里的细小违规内容根本看不到，必须要点进去看大图。但审核工作台没有点击图片放大的功能。

**总结评级：**

| 模块 | 评级 | 一句话总结 |
|------|------|-----------|
| 登录/注册 | 需改进 | 流程合理，但登录成功后用户信息可能为空时缺乏防御性检查 |
| 业务看板 | 需改进 | 展示清晰但数字有误导性，负责人下拉列表有严重数据源 bug |
| 审核工作台 | 需改进 | 核心审核流程可用，但缺少排序和批量操作这两大效率刚需 |
| 申诉管理 | 需改进 | 处理流程完整，但只能看未处理记录、无图片预览 |
| 直播电视墙 | 需改进 | 实时刷新和高风险高亮到位，但缺少点击跳转审核入口 |

**是否达到可交付标准：** 当前版本达到了"可用"标准（core audit loop 能跑通），但距离"好用"和"可交付给客户"还有差距。核心短板是审核工作台缺少排序/批量/放大三大效率功能，建议在下一阶段开发中优先补齐。
