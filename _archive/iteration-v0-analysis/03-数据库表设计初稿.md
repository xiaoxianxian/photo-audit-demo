# 3. 数据库表设计初稿

## 核心表概览

共设计 **7 张核心表**，覆盖上传、审核、申诉、用户、日志五大业务域。

---

## 表 1：users（用户表）

存储摄影师、审核员、管理员账号。

| 字段 | 说明 |
|------|------|
| id | 主键，UUID |
| username | 用户名，唯一 |
| display_name | 显示名（如 @alex_photo） |
| role | 枚举：`photographer` / `reviewer` / `admin` |
| email | 邮箱 |
| created_at | 注册时间 |
| is_active | 是否启用 |

**关联：** 一对多关联到 photos（上传者）和 audit_logs（操作者）。

---

## 表 2：photos（作品表）

每上传一张图片产生一条记录。

| 字段 | 说明 |
|------|------|
| id | 主键，UUID |
| uploader_id | 外键 → users.id（摄影师） |
| file_name | 原始文件名 |
| file_size | 文件大小（字节） |
| mime_type | 文件类型（image/jpeg 等） |
| thumbnail_url | 缩略图存储路径 |
| original_url | 原图存储路径 |
| width / height | 图片尺寸 |
| upload_time | 上传时间 |
| status | 枚举：`pending` / `approved` / `rejected` / `appealed` |

**关联：** 一对一关联到 ai_reviews；一对多关联到 audit_logs。

---

## 表 3：ai_reviews（AI 审核结果表）

AI 机审的结构化输出。

| 字段 | 说明 |
|------|------|
| id | 主键，UUID |
| photo_id | 外键 → photos.id |
| model_name | 使用的模型（gemini-2.0-flash / gpt-4o 等） |
| score | 安全评分（0-100） |
| is_safe | 布尔值，AI 判定是否安全 |
| reason | AI 给出的审核理由（文本） |
| categories | JSON 数组，多维度标签（如 `["quality","copyright"]`） |
| consistency_score | 裁判模型一致性分数（可选，DeepSeek 校验用） |
| judge_comment | 裁判模型评论（可选） |
| created_at | AI 审核时间 |

**关联：** 一对一关联到 photos。

---

## 表 4：audit_records（人工审核记录表）

审核员的操作记录。

| 字段 | 说明 |
|------|------|
| id | 主键，UUID |
| photo_id | 外键 → photos.id |
| reviewer_id | 外键 → users.id（审核员） |
| action | 枚举：`approve` / `reject` |
| reject_reason | 打回原因（版权争议 / 画面模糊 / 政治敏感） |
| comment | 审核员备注 |
| created_at | 操作时间 |

**关联：** 多对一关联到 photos 和 users。

---

## 表 5：appeals（申诉表）

摄影师申诉记录。

| 字段 | 说明 |
|------|------|
| id | 主键，UUID |
| photo_id | 外键 → photos.id |
| photographer_id | 外键 → users.id（申诉人） |
| appeal_reason | 申诉理由（文本） |
| status | 枚举：`submitted` / `under_review` / `resolved_approved` / `resolved_maintained` |
| reviewer_id | 外键 → users.id（复核审核员，可为空） |
| review_comment | 复核结果备注 |
| submitted_at | 申诉提交时间 |
| resolved_at | 申诉解决时间 |

**关联：** 一对一关联到 photos（一张照片可申诉多次，但通常一次）；多对一关联到 users。

---

## 表 6：audit_logs（操作日志表）

全量操作审计，不可篡改。

| 字段 | 说明 |
|------|------|
| id | 主键，自增 |
| operator_id | 外键 → users.id（操作人） |
| action_type | 枚举：`upload` / `approve` / `reject` / `appeal` / `config_change` |
| target_type | 枚举：`photo` / `user` / `system` |
| target_id | 关联对象的 ID |
| detail | JSON，操作详情（如打回原因、申诉理由等） |
| created_at | 操作时间 |

**关联：** 多对一关联到 users。

---

## 表 7：system_config（系统配置表）

AI 模型配置、审核规则等。

| 字段 | 说明 |
|------|------|
| id | 主键，自增 |
| config_key | 配置键（如 `ai_primary_model` / `api_key_gemini`） |
| config_value | 配置值 |
| description | 配置说明 |
| updated_by | 外键 → users.id（修改人） |
| updated_at | 修改时间 |

**说明：** API Key 等敏感信息应加密存储。

---

## 表关系图（文字版）

```
users (1) ────── (N) photos
  │                      │
  │                      ├─ (1) ai_reviews
  │                      ├─ (N) audit_records
  │                      └─ (N) appeals
  │
  ├─ (N) audit_logs
  └─ (N) system_config (updated_by)

audit_records (N) ─── (1) photos
appeals     (N) ─── (1) photos
ai_reviews  (1) ─── (1) photos
```

---

## ER 关系总结

- **users ↔ photos**：一个摄影师可上传多张照片（1:N）
- **photos ↔ ai_reviews**：每张照片有且仅有一条最新 AI 审核结果（1:1）
- **photos ↔ audit_records**：一张照片可被多次人工审核操作（1:N）
- **photos ↔ appeals**：一张照片可提交申诉（1:N）
- **audit_logs**：全量表，关联 users（谁操作的）+ 目标对象（照片/用户/系统）
- **system_config**：独立配置表，记录修改人
