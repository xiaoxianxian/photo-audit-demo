# 2. 技术选型评估

## 评估维度

| 维度 | 说明 |
|------|------|
| **并发量** | MVP 阶段预计日审核量 100~500 张，峰值并发 5~10 人同时在线审核 |
| **数据量** | 初期图片存储 < 10GB，审核记录 < 10 万条/年 |
| **部署环境** | 内部使用，可能部署在公司内网或私有云，不面向公网大规模用户 |
| **团队现状** | 前端已有 React + Tailwind 基础（项目中有 `frontend/` 目录和 `package.json`） |
| **AI 集成** | 需要对接多个 AI 模型（Gemini/GPT/Kimi），后端作为代理更安全 |

---

## 方案对比

### 方案 A：React + Node.js/Express + PostgreSQL（推荐）

| 方面 | 说明 |
|------|------|
| **前端** | React 18 + TypeScript + Tailwind CSS + Ant Design / Shadcn UI |
| **后端** | Node.js + Express / Fastify + TypeScript |
| **数据库** | PostgreSQL（关系型，适合审核记录 + 用户管理） |
| **对象存储** | MinIO（自建 S3 兼容）或阿里云 OSS |
| **优点** | 1. 前后端同语言（TS），开发效率高<br>2. TS 类型安全，减少运行时 bug<br>3. Postgres 成熟稳定，支持事务和复杂查询<br>4. 社区生态丰富，AI SDK（langchain、vercel-ai）对 Node.js 支持最好<br>5. 未来扩展性强（微服务拆分方便） |
| **缺点** | 1. 相比 Python 方案，AI/ML 领域生态稍弱<br>2. Node.js 高 CPU 场景性能不如 Go/Rust |
| **适合场景** | 团队有 JS/TS 经验，AI 调用以 HTTP API 为主，非自研模型 |

### 方案 B：React + Python(FastAPI) + PostgreSQL

| 方面 | 说明 |
|------|------|
| **前端** | React 18 + TypeScript + Tailwind CSS |
| **后端** | Python + FastAPI + SQLAlchemy |
| **数据库** | PostgreSQL |
| **对象存储** | MinIO / 阿里云 OSS |
| **优点** | 1. Python 是 AI/ML 首选语言，后续若需自研审核模型很方便<br>2. FastAPI 自动生成交互文档（Swagger），前后端联调友好<br>3. 生态好（Pillow 图像处理、pydantic 数据校验）<br>4. 后端 AI 逻辑和前端分离清晰 |
| **缺点** | 1. 前后端语言不同，团队需掌握两种语言<br>2. Python 部署和运维复杂度略高于 Node.js<br>3. 并发性能不如 Go（但对当前量级无影响） |
| **适合场景** | 团队有 Python 经验，或未来可能涉及自研 AI 模型训练 |

### 方案 C：Next.js 全栈 + SQLite（轻量方案）

| 方面 | 说明 |
|------|------|
| **前端 + 后端** | Next.js 14+ (App Router) + Server Actions |
| **数据库** | SQLite（通过 Prisma ORM） |
| **对象存储** | 本地文件系统或云存储 |
| **优点** | 1. 最简架构，一个项目搞定前后端<br>2. SQLite 零运维，单文件数据库，适合小团队<br>3. 开发速度最快，适合 MVP 快速迭代<br>4. 部署简单，Vercel/ Railway 一键部署 |
| **缺点** | 1. SQLite 并发写入能力有限（>100 并发写会瓶颈）<br>2. 数据迁移到 Postgres 成本高<br>3. Server Actions 调试和测试不如传统 API 成熟<br>4. 多人协作时 Git 冲突可能更多 |
| **适合场景** | 超小型团队（<5 人），快速验证市场，短期 MVP |

|------|----------------------|---------------------|-------------------|

## 明确建议：方案 A（React + Node.js + PostgreSQL）

**推荐理由：**

1. **语言统一**：前后端都用 TypeScript，代码复用率高（类型定义、API 契约可共享）
2. **AI 集成够用**：当前 AI 审核走 HTTP API（Gemini/GPT），Node.js 的 `@google/generative-ai` 和 OpenAI SDK 都是官方一等公民支持
3. **PostgreSQL 是通用选择**：审核记录需要事务保障（通过/打回不能丢数据），Postgres 成熟可靠
4. **团队基础**：项目中已有 `frontend/` 目录和 React 技术栈，说明团队熟悉 JS/TS 生态
5. **未来可扩展**：日审核量从 500 涨到 5 万，架构不需要大改

**如果团队有 Python 基础且计划自研审核模型**，则选方案 B。否则方案 A 是最稳妥的选择。
