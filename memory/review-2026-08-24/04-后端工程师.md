## 二、Bug（确认级，需修复）🐛

### B1.【严重】`getDB` 的 sync.Once 错误被闭包吞掉 — 连接失败返回 `(nil, nil)`
`cmd/server/main.go:37-62`
```go
var err error
dbOnce.Do(func() {
    cfg, err := pgxpool.ParseConfig(dsn)   // ← ":=" 在闭包内新建了 err
    ...
})
return dbPool, err   // 外层 err 恒为 nil
```
闭包内 `cfg, err :=` 遮蔽外层 `err`。数据库连不上时返回 `(nil, nil)`，`main` 判定成功继续启动，首个请求 nil pointer panic。**修复**：闭包内改用 `=` 赋值，或让 Do 返回 error。

### B2.【严重】跨租户数据泄漏：审核相关查询完全没有 tenant 过滤
- `elementRepo.FindByStatus` / `CountByFilters` **签名里就没有 tenantID 参数**
- `ReviewHandler.ListPending`、`ElementStats` 忽略 `c.Locals("tenant_id")`
- `LogRepository.ListAllFiltered`（`GET /review/logs`）全局列出**所有租户**的审核记录
- `GetElementsByContent` 只按 contentID 查，不校验归属

租户中间件辛苦解析并校验了 tenant_id，但这些 handler 根本没用。任何租户的审核员能看到全平台待审队列和日志。CLAUDE.md 声称“数据库层 RLS 过滤”，代码中未见 RLS 依据。**修复**：给上述 repo 方法加 tenantID 参数（join contents），或真正启用 RLS。

### B3.【严重】公开注册接口可自授 `platform_admin`
`POST /api/v1/auth/register` 无需鉴权，而 `jwt.go ValidRoles` 包含 `"platform_admin": true`，`AuthService.Register` 直接接受任意合法 role。任何人可注册平台超管。**修复**：公开注册仅允许普通角色，特权角色走管理员创建流程。

### B4.【高】`ResolveAppeal` 把 content ID 写进 `audit_records.element_id`
`review_service.go:238`
```go
ElementID: appeal.ContentID,   // ← 应该是 element ID
```
字段语义污染，后续 `FindByElementID` 的审核历史查询会把这条改判记录挂到错误的 element 上。

### B5.【高】`HumanReview` 非事务 + check-then-act 竞态
`review_service.go:92-131`：
1. 先读 `elem.HumanStatus` 判断是否已审，再 `Create(audit_record)`，再 `UpdateStatus`——三步无事务。第二步成功第三步失败 → 有判罚记录但元素仍 pending，可再次审核产生重复记录；
2. 两个并发请求都能通过第 92 行检查 → 双重判罚。
**修复**：改为单条守卫更新 `UPDATE ... SET human_status=$1 WHERE id=$2 AND human_status='pending_human'` + RowsAffected 检查（和你们在 appeal 上做的乐观锁同款），audit_record 插入放进同一事务。

### B6.【高】goroutine 持有 fiber 的 `c.Context()` — 请求结束后上下文被复用/取消
`content_handlers.go:164`：`go h.ingestionSvc.TriggerAIReview(c.Context(), ...)`。fasthttp 的 RequestCtx 在 handler 返回后即被回收复用，异步 AI 审核（30s 超时的外部调用）会在随机时刻读到脏数据或被取消。`review_service.HumanReview:135` 同样把请求 ctx 传进 goroutine 给 `TriggerContentDecision`。已知遗留清单提到"context.Background()"问题，这里是更危险的变体。**修复**：`ctx, cancel := context.WithTimeout(context.Background(), N)` 传入 goroutine。

### B7.【高】`config.JWTMinLength` 校验形同虚设
`config.go:47` 只有 `mapstructure:"JWT_MIN_LENGTH"` tag，但整个项目没有任何 mapstructure 加载逻辑，字段恒为零值 0。`main.go:87` 的 `len(cfg.JWTSecret) < 0` 永远为 false——最小长度防线不存在。另外 `JWTExpiry` 被解析了两次（L111 和 L136 重复），`GenerateToken` 也硬编码 24h 没用上配置。

### B8.【中】JWT secret 缺失时静默生成随机值
`config.go:126-128`：多实例部署或重启后每个进程 secret 不同 → 全部 token 失效/互不认账，且无告警。生产应要求显式配置，开发模式才允许随机生成（打 WARN 日志）。

### B9.【中】`StreamScheduler.isStreamHealthy(nil, "")` 必然失败
`stream_scheduler.go:106`：`GetActiveStreams(nil, "")` —— pgx 拿到 nil ctx 有 panic 风险；即使不 panic，`WHERE tenant_id = $1` 绑定空串匹配不到任何行 → 返回 not-found → 所有活跃直播被判离线并下线。这段调度器目前等于“定时把所有直播标记 offline”。

### B10.【中】WebSocket Hub 的 double-close panic 风险与 Run 泄漏
`websocket_hub.go`：
- `Stop()` 对所有 client `close(client.send)`；之后若 `Run` 循环还在处理残留的 unregister 消息，会对同一 channel 再次 `close` → panic。`Broadcast*` 的 default 分支也 close，与 Stop 竞态同理；
- `Run()` 的 select 没有 stop 分支，`Stop()` 之后 goroutine 永久泄漏；
- 建议：close 交给唯一属主（Run 循环），Stop 通过向 register/unregister channel 发哨兵或单独 done channel 实现。

### B11.【低】迁移器失败路径会导致全量重放
`main.go:264-273`：`SELECT version FROM schema_migrations` 出错时 `applied == nil` 且不报错，后续所有 migration 重跑，`INSERT` 主键冲突才失败——启动即 fatal 且报错信息误导。另外逐文件 `rows.Scan(&v)` 错误被忽略、每个 migration 未包在事务里（半途失败留下脏 schema）、`fmt.Sscanf` 错误忽略。

### B12.【低】`parseJudgeResponse` 兜底返回 0 分制造假分歧
`ai_service.go:377`：裁判模型输出无法解析出 score 时返回 0，`diff>20` 几乎必然触发 → 元素被错误标记 `is_conflict` 升级人审。应该返回 error 让调用方跳过裁判环节，而不是伪造一个 0 分。

## 三、不好的地方 / 设计与一致性问题 ⚠️

1. **API 错误响应三种风格混用**：
   - `responder.ok/error`：HTTP 200 + body `{code:0}`（Auth/Tenant 系列）
   - review/content 系列：正确设置 HTTP status + `{code, message}`
   - `middleware/auth.go:33`：**401 场景忘了 `c.Status(401)`**，实际返回 HTTP 200 + code:401；`tenant.go` 里又有 `{error:{message,code}}` 嵌套结构。
   与 CLAUDE.md 承诺的 RFC 7807 相去甚远。建议统一 responder 并全局收口。

2. **内部错误信息直接透给客户端**：几乎所有 500 响应拼 `err.Error()`（含 SQL 错误细节），`defaultErrorHandler` 同样裸吐。信息泄露 + 日志与响应耦合。应返回通用文案，细节进日志。

3. **`BatchReview` 非原子且 N+1**：循环调用单条 `HumanReview`，每个元素 2~3 次 DB roundtrip + 各自触发一次 `go TriggerContentDecision`（N 个 goroutine 抢同一把 per-content 锁）。中途失败前面已提交的部分不回滚，却对客户端返回整体 500。要么包事务，要么明确返回逐条结果（207 风格）。

4. **`PUT /api/v1/appeals/:id` 是个旁路后门**：`AppealHandler.Update` 接受 body 里任意 `status/decision/reviewer_id`，走的是 `appealRepo.Update`——**没有乐观锁守卫**，可以改写已 resolved 的申诉、可以伪造 reviewer_id。与 `PUT /review/appeal/:id` 功能重叠但约束弱得多。建议删除或收紧到与 ResolveAppeal 一致。

5. **鉴权中间件每请求执行两次**：routes 里 `protected` 组挂了 `authMW`，`tenantMW` 内部又调一遍 `auth(c)`——每请求解析两遍 JWT + tenant 中间件额外一次 users 表 EXISTS 查询。tenant 中间件应信任 Locals 已有身份，或去掉外层 authMW。

6. **platform_admin 触发类型断言 panic**：`Tenant` 中间件对 platform_admin 设置 `tenant_bypass` 而**不设 tenant_id**，下游 `c.Locals("tenant_id").(string)`（如 `HumanReview:232`）对 nil 断言直接 panic（被 recover 吃成 500）。应使用带 ok 的断言并给出 400。

7. **限流策略一刀切**：全局 100 req/15min/IP，审核员工作台一次页面加载就会消耗大量配额，正常使用会被 429。至少登录接口单独收紧、业务接口放宽或按用户维度限。

8. **`AuthService.Login` 死代码**：`errors.Unwrap` 检查 `ErrInvalidPassword` 的分支永远不可达（repo 包装的是 `pgx.ErrNoRows`）。无害但迷惑读者。另外用户不存在时不做 dummy bcrypt 比较，存在时序侧信道可枚举用户名（好消息是响应文案已统一）。

9. **MinIO presigned URL 当持久数据存**：`UploadObject` 生成 7 天有效 URL 直接写进 `element_content`——过期后前端图片全裂。应存 object name，读取时按需签发短时效 URL。文档声称按租户分 bucket，实现是单一 bucket（对象 key 无租户前缀隔离）。

10. **`UploadFile` 整文件读入内存**：100MB 文件 × 并发请求数直接放大内存；`processVideoAsync` 又完整持有一份 `videoData []byte` 且 goroutine 数量不受限。建议流式传 MinIO、视频预处理加全局 worker pool。

11. **`file://` mock URL 与 SSRF 校验互相矛盾**：无 MinIO 时生成 `file://xxx` 存库，后续 `validateURL` 会因 scheme 拒绝——开发路径自己打自己。

12. **`DetectQuotaError` 关键词匹配过宽**：任意非 200 响应体包含 "insufficient"/"quota" 即判定额度错误并静默切 fallback，真实故障（如 5xx 带错误详情）会被掩盖成降级成功。建议只在 402/429 生效，其余状态原样抛错。

13. **杂项**：
    - `envOr` 注释说会尝试大小写变体，实现并没有；
    - `pgxpool MaxConns=100/MinConns=10` 硬编码在 main，应入 config；
    - `redactURL` 返回常量字符串，函数名与行为不符（不如直接不打 DSN）；
    - `CreateWithTx`（log/appeal）插入后不回填 `created_at`，返回对象的 CreatedAt 为零值，与非 tx 版本不一致；
    - `RejectReason` 枚举未做白名单校验就入库；
    - `probeResolution` 的 `strconv.Atoi` 错误忽略（w/h 可能为 0，靠后续 `>0` 判断兜住，能接受但不严谨）；
    - 4 个 repo 文件（appeal/ai_config/live_wall/quality）缺 `rows.Err()` 检查，迭代中断会静默截断结果集。

## 四、可优化项 🔧

1. **`HumanReview` 三段式改成单事务 + 守卫更新**（同时解决 B5 与重复审核）。
2. **`SubmitAppeal` 的事务内 SELECT 检查在 READ COMMITTED 下挡不住并发双插**（两个事务互相看不见未提交行）——目前靠 DB UNIQUE 约束兜底是对的，但要把 `pgconn.PgError 23505` 映射为 `ErrAlreadyAppealed`，否则并发场景客户端收到 500 而不是 409。
3. **租户成员校验加缓存**：`Tenant` 中间件每请求一次 users 表查询，可用短 TTL 缓存（如 30s）。
4. **`TriggerAIReview` 中 `UpdateAIRisk` 与 `UpdateStatus` 两条 UPDATE 可合并**，减少一半往返并消除中间态窗口；conflict 信息通过 `errCh` 传递属于绕路，直接日志即可。
5. **审计记录分区表的查询都带 `created_at` 过滤会更友好**——现在 `ListAllFiltered` 全表扫后 ORDER BY created_at DESC，分区裁剪完全用不上。
6. **结构化错误类型替代字符串匹配**：`strings.Contains(err.Error(), "access denied")` / `"already exists"` 散落在 handler 层，应定义 sentinel error（`model.ErrAlreadyReviewed` 已是好例子，推广它）。
7. **`GetDashboardStatsConsolidated` 思路很好**，同类合并思路可应用到 reviewer 绩效统计。

## 六、总结

这轮安全修复（CORS/bcrypt/BodyLimit/乐观锁/Create Scan）质量不错，方向正确、实现到位。但当前最危险的问题不在已修的这几处，而在**三条老主线**上：① 租户隔离在查询层缺失（B2，多租户系统的致命伤）；② 公开注册可提权（B3）；③ 异步链路的 ctx 与并发治理粗糙（B6/B10）。加上 `getDB` 这个一触即发的 err 遮蔽 bug（B1），建议在下一个迭代把 P0/P1 清掉再谈功能扩展。
