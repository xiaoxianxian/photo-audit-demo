## 一、做得好的地方

1. **核心链路数据模型完整且分层清晰**：`contents → content_elements → audit_records` 的元素级审核粒度是行业正确做法（图片/标题/评论/ASR 文本分别审），`audit_records` append-only + `ai_score_before/after` 字段保留了完整判罚证据链，为质检与申诉追溯提供了数据基础。
2. **裁判分歧可视化做了闭环**：`content_elements.is_conflict` 字段 → 部分索引（`WHERE is_conflict=true`, init.sql:338）→ 前端橙色高亮 + Tooltip「请重点审核」（Review.tsx:118-124），从字段到 UI 一路贯通。
3. **申诉唯一性约束落在数据库层**：`uq_appeals_content_applicant UNIQUE(content_id, applicant_id)`（init.sql:403）+ 服务层 `ErrAlreadyAppealed` 双保险，比纯应用层校验可靠。
4. **防疲劳误审的产品细节难得**：连续通过 ≥5 次触发二次确认弹窗和快捷键拦截（Review.tsx:211, 414-424），说明开发时考虑了真实审核员的“手滑”场景。
5. **reviewer_id 强制取自 JWT**：三个 handler 均有注释明确禁止信任请求体的 reviewer_id，防止代审核/伪造绩效——这是很多同类 demo 会漏掉的。
6. **多租户意识贯穿**：路由统一挂 tenantMW，HumanReview 校验元素所属 content 的租户归属（review_service.go:84-90）。
7. **AI 降级链路完整**：Agnes 主审 + DeepSeek 裁判 + 本地规则 fallback + 402/429 自动切换，商业上保证了“额度耗尽不停摆”。

## 二、不好的地方 & Bug（按严重度）

### P0 — 直接破坏功能闭环

| # | 问题 | 位置 | 产品影响 |
|---|------|------|---------|
| B1 | **改判时把 content_id 写进 element_id 字段**：`ResolveAppeal` 构造的 AuditRecord 中 `ElementID: appeal.ContentID`（review_service.go:238），而 `audit_records.element_id` 是 `NOT NULL REFERENCES content_elements(id)`。内容 ID ≠ 元素 ID，**外键必然违约，事务回滚 → 所有“改判通过”操作失败** | review_service.go:236-247 vs init.sql:348 | 申诉改判（用户最敏感的公平性场景）大概率整体不可用 |
| B2 | **audit_tasks 表根本不存在**：CLAUDE.md 和 ER 图宣称核心链路是 `contents → content_elements → audit_tasks → audit_records`，但 init.sql 无该表，全代码库无引用；`audit_records.task_id` 只能落零值默认 `'0000...-0000'`（init.sql:347） | 全局 | 文档承诺与实现脱节；未来做任务分配/抢单模式时无承接结构 |
| B3 | **penalty_level_code（判罚等级）字段全程无人写入**：表设计了 `tenant_audit_levels` 判罚等级配置 CRUD，但人工打回（HumanReview）从不接收 penalty_level，`appeals.penalty_level_code` 也无写入路径 | review_service.go:101-111、routes.go | “判罚等级”是租户付费配置的核心卖点之一，目前是空转功能：配了也没用 |

| # | 问题 | 位置 | 说明 |

| D1 | **Esc 快捷键=无原因秒打回**：按 Esc 直接以 `'快捷键打回'` 作为 reason 执行 reject（Review.tsx:428），绕过 6 类违规原因分类。审核日志里会大量出现非枚举 reason，污染后续按原因统计的能力（RejectReason 枚举形同虚设——DB 层 reason 只是 VARCHAR 无 CHECK） | Review.tsx:428、model/audit_record.go:33-40 | 高风险误操作 + 数据脏化双重问题 |

### P2 — 优化建议

1. **PRD 与实现严重漂移**：prd.md 描述的还是 v0 单机 localStorage 版本（Gemini/DeepSeek 双模型、localStorage 持久化、固定 99.2% 召回率假数据），与现在的 Go+PG 多租户架构完全是两个产品。PRD 应重写，否则新成员 onboarding 会被误导。
2. **审核时效指标缺失**：PRD 核心指标“平均出审时效 <1.2s”没有落地字段——audit_records 只有 created_at，没有“任务领取时间”，无法计算人审耗时；Dashboard 的 reviewer 绩效 avg_time 来源存疑。
3. **抽检准确率/召回率口径不完整**：QualityAuditStats 只有 disagree_rate/avg_qa_score，没有 PRD 承诺的准确率、召回率、风险水位；召回率需要“全量复核”才能算，抽样设计里没体现。
4. **通知系统是 ConsoleNotifier**：申诉结果“通知申诉人”实际只打到服务端 stdout，摄影师在产品内收不到任何结果反馈——闭环断在最后一公里。前端也无消息中心页面。
5. **上传入口放在审核员工作台**（Review.tsx:559-587）：创作者上传和审核员审核混在同一角色页面，与 RBAC 四角色的产品定位矛盾；摄影师角色没有自己的“我的作品/审核进度”视图。
6. **申诉入口断裂**：SubmitAppeal 需要 contentId 手输 URL（/appeal/new/:contentId），被打回的用户在界面上没有任何地方能看到“哪些内容被打回、点这里申诉”——申诉闭环的起点是靠猜 URL。
7. **分页硬编码 page_size=50 且 Table pagination 固定配置**（Appeal.tsx:248）：申诉量大时只能看到前 50 条待处理。
8. **直播电视墙 viewer_count 字段无来源**：live_streams.viewer_count 无任何更新路径，前端若展示会是永远为 0 的假数据。

## 三、可增加 / 可调整的方向（商业价值视角)

1. **审核 SLA 与队列深度看板**：增加 `audit_tasks.claimed_at/completed_at`，输出“积压量、平均停留时长、超时告警”——这是向租户证明付费价值（AI 替省多少人力）的核心报表。
2. **AI 机审与人审的一致率报表**：现在有 ai_score_before/after 数据，完全可以算“AI 建议被采纳率”，用于说服租户提升 AI 自动通过阈值、降低人审成本——这是续费话术。
3. **打回原因结构化 + 申诉成功率反哺规则引擎**：tenant_audit_rules 已有 rule_expression 字段但无执行引擎消费它；建议用申诉改判率自动建议规则调整，形成“判罚→申诉→规则迭代”飞轮。
4. **审核员双人复核 / 仲裁流**：is_conflict 元素目前仍由单人处理，高风险分歧内容建议强制的 second reviewer 流程（audit_team_members.senior_reviewer 角色已预留但未被业务使用）。
5. **摄影师端通知与站内信**：Notifier 抽象已在，接 WebSocket/邮件即可补齐申诉闭环最后一步，成本低收益高。
6. **软删除/回收站**：所有 DELETE 均物理删除（rules/levels/words/teams），租户管理员误删配置无法恢复，SaaS 产品应有至少 soft-delete。

## 四、结论

Phase 1 MVP 的**骨架质量高于一般 demo**：多租户隔离、审计链路、降级策略、防疲劳交互都有真实产品思维。但存在 3 个 P0：**改判外键违约（B1）、audit_tasks 表缺失（B2）、判罚等级空转（B3）**——其中 B1 意味着“申诉改判”这一宣传中的核心闭环很可能从未真正跑通过，建议优先验证并修复。其次是打回原因数据口径（D1/D2/D4）会长期污染运营数据，越早治理成本越低。PRD 文档需彻底重写以匹配当前架构。
