# 【普通用户】Photo Audit Demo 使用旅程评审报告

> 角色：普通用户（分别代入 内容创作者 / 审核员 / 租户管理员 三种视角）
> 方法：只读代码走查 + 交互流程模拟，未运行系统、未修改任何文件

## 一、使用旅程逐步体验评价

### 第 1 步：注册（Register.tsx）

| 项目 | 评价 |
|---|---|
| 体验 | ⭐⭐⭐ 中等偏下 |
| 做得好 | 密码强度实时提示（PasswordStrength）、确认密码二次校验、国家代码格式校验、“已有账号？登录”入口清晰 |

**障碍与问题：**
1. **🔴 角色被写死为 `reviewer`**（`api.ts` L81：`role: 'reviewer'`）。创作者、质检员无法通过注册获得对应角色——而整个平台的核心叙事是“创作者上传→申诉”，注册流程却只造出审核员。角色断在第一步。
2. **🔴 选了租户但没传给后端**：注册页让用户选/建租户得到 `tenantId`，但 `postRegister()` 根本不接收 `tenant_id` 参数，只在前端 userInfo 里塞了一份本地假象。刷新后用户与租户的关联实际不存在。
3. **🔴 未登录即可拉取全部租户列表**（`getTenants` 在挂载即调用，无鉴权前置），任何访客都能枚举所有租户名称——多租户平台的信息泄露。
4. 任何人都能“创建新租户”（POST /tenants 无门槛），没有邀请码/管理员审批概念。
5. 没有“忘记密码”、“用户协议”勾选；邮箱标注可选但不填则无法找回账号。

### 第 2 步：登录（Login.tsx）

- ⭐⭐⭐⭐ 简洁顺畅。表单校验、错误提示、跳转注册链接齐全。
- 缺失：忘记密码入口、租户维度提示（登录后不知道自己属于哪个租户）、角色说明。

### 第 3 步：进入首页仪表盘（Dashboard.tsx）

| 项目 | 评价 |
|---|---|
| 体验 | ⭐⭐⭐ 信息全但混乱 |

**做得好：**
- 待审元素 > 0 时顶部黄色提醒条 + 一眼可见的统计卡（今日已审/通过率/驳回率/平均风险分/分歧数）；
- 近 7 天趋势用纯 CSS 柱状图实现，hover 有明细 tooltip；
- 五个数据源 `Promise.allSettled` 并行加载，互不阻塞。

**障碍与问题：**
1. **🔴 所有角色看到同一张首页**：普通审核员登录后直接面对“新建租户/删除租户/新建团队”按钮——点了必然 403。菜单也不按角色裁剪（Layout.tsx 的 MENU_ITEMS 是静态全量），路由守卫只做静默重定向到 `/review`，用户不知道“为什么菜单里有的点不进去”。缺少 403 提示页。
2. **🟡 团队负责人下拉框只有你自己**（L506-514：`leaders` 仅由 currentUser 构成），实际上永远只能任命自己当组长——功能形同虚设。
3. 🟡 团队成员角色选项是“管理员/编辑者/查看者”（admin/editor/viewer），与平台三级 RBAC（platform_admin/tenant_admin/reviewer/quality_checker）完全对不上，配置了也不生效。
4. 🟡 删除租户只有一句 Popconfirm，没说明会级联删除多少内容/用户——高危操作警示不足。
5. 🟡 “待审元素 N 个”提醒条不可点击，看完还得自己去侧边栏找“审核工作台”。

### 第 4 步：上传内容（Review.tsx 上传区）

**做得好：**
- 拖拽大区域 + 类型/大小前端预检（图片/视频、100MB），提示文案明确；
- 上传后有 Spin 反馈和成功 toast（含内容 ID 前 8 位）。

**障碍与问题：**
1. **🔴 上传入口放在“审核工作台”里，这是最大的信息架构错位**。创作者想传图，却要进一个满是“通过/打回/批量审核”按钮的审核员界面；上传后自己的内容混在别人的待审队列里。
2. **🔴 上传后无处可看结果**。成功 toast 显示了一个截断的内容 ID，但全站没有“我的内容/我的投稿”页面：看不到机审分数、不知道过没过、更不知道去哪申诉。toast 里的 ID 也无法点击复制跳转。
3. 🔴 上传成功 ≠ 审核可见：图片走异步 AI 审核，但页面只是简单 `fetchElements()`，新上传内容大概率还不在列表里，用户会以为“传丢了”。
4. 🟡 `multiple={false}` 不支持批量；标题自动取文件名、描述留空且不可编辑，没有上传前元信息表单。
5. 🟡 风险分区间 Slider 用 `onChange` 每拖一格就触发一次请求，无防抖，数据量大会卡。

### 第 5 步：AI 机审 → 人工审核（Review.tsx 工作台）

**做得好（这部分是全站亮点）：**
- 卡片网格 + 风险分色标 Tag + 置信度 + 机审状态标签，信息密度合适；
- 裁判分歧橙色边框高亮 + “分歧”Tag + tooltip 引导重点审核；
- 键盘快捷键（←→切换、Enter 通过、Esc 打回）+ 快捷键提示条 + 底部帮助弹窗；
- 连续通过 ≥5 次触发确认警告（防机械误审）——很贴心的细节；
- WebSocket 实时连接状态指示灯 + “新任务 N 条（点击刷新）”；
- 统计栏（待审/已通过/已打回/分歧）+ 批量选择/批量通过/批量打回。

**Bug 与障碍：**
1. **🔴 快捷键绕过安全确认**：鼠标点击“通过”有 Popconfirm 二次确认，但 Enter/Space 直接调 `handleApprove` 跳过确认；“Esc 打回”更是零原因瞬间打回（reason='快捷键打回'）。两套操作路径安全等级不一致，误触代价极高。
2. **🔴 打回原因选择器交互断裂**（L246-257）：`Select mode="tags"` 的 onChange 在选中第一项时立即提交并关闭——想勾两个原因根本做不到；而且 tags 模式允许随手输入任意文本当理由提交。
3. **🔴 帮助弹窗承诺了不存在的快捷键**：HelpModal 写着 "Shift+Enter 批量通过已选元素"，代码里没有实现。
4. 🟡 批量打回原因是硬编码的 `'批量打回'`（L321），没有让审核员选原因，违反自家“打回必选原因”的正例设计。
5. 🟡 打回原因值存的是英文枚举（copyright/porn…），审核日志页原样展示英文，中国用户看不懂。
6. 🟡 AI risk_types 也是原始英文标签直接渲染成红色 Tag。
7. 🟡 卡片上没有内容归属（creator/时间/所属内容 ID），审核员无法判断上下文。

### 第 6 步：短视频审核（ShortVideoReview.tsx）

1. **🔴 视频"播放器"播的是封面图**：`videoUrl = elements.find(e => e.element_kind === 'cover_image')?.element_content`（L64）——把封面图 URL 塞进 `<video>`，审核员根本放不出视频，等于盲审视频内容。应为原视频 file_url。
2. **🔴 “全部通过”只通过了第一个元素**：`onApprove(elements[0]?.id)`（L250）——按钮叫“全部通过”，实际只处理 1 个元素，语义欺骗，会造成大面积漏审。
3. **🔴 元素加载方式错误**：先拉 `getPendingElements({page_size:100})` 再前端按 content_id 过滤——超过 100 条时元素丢失，且把全租户待审数据都拖到浏览器。
4. 🟡 状态列直接显示英文 `approved/rejected`；分页 `_setPage` 从未接线，翻页无效（AuditLog 页同样问题，永远停在第 1 页）。
5. 🟡 打回原因选项与图片端不一致（这里多了 low_quality 少了 blur），同类内容两套标准。

### 第 7 步：被打回 → 申诉（SubmitAppeal.tsx / Appeal.tsx）

**这是旅程中断裂最严重的一环：**

1. **🔴 申诉入口不存在**。路由 `/appeal/new/:contentId` 和提交页都写好了，但**全站没有任何一个按钮/链接指向它**——被打回的创作者没有任何 UI 入口发起申诉。这条核心闭环在产品层面是断的。
2. **🔴 没有“我的申诉”视图**。`/appeals` 页面列出的是**全租户所有申诉 + 处理按钮（改判/维持）**，且该路由没有角色守卫——普通用户进来看到的是管理员的处理台，理论上能把自己的申诉“改判通过”（前端层面）。创作者视角完全缺位。
3. 🔴 `SubmitAppeal.tsx` 在 render 函数体里直接调 `message.error()` + `navigate()`（L21-31）——React 反模式，会引发渲染期副作用。
4. 🟡 证明材料只支持贴 URL 文本，不支持上传文件——对普通创作者门槛偏高。
5. 🟡 申诉详情弹窗有三个提交动作：底部默认 OK 按钮（隐藏逻辑是“维持原判”）+ 维持原判 + 改判通过，三个按钮两种结果并存，容易误触；列表行的快捷图标与弹窗功能重复。
6. ✅ 做得好：申诉仅一次的提示、状态四态标签（待审核/审核中/已改判/维持原判）、详情弹窗内嵌原始 AI 结果供比对。
7. ❌ 但“结果将通知您”落空：通知是 ConsoleNotifier（后端控制台打印），前端无任何站内信/消息中心，申诉人永远收不到结果。

### 第 8 步：直播电视墙（LiveWall.tsx）

**做得好：** LIVE/OFFLINE 徽章、风险分角标、高风险橙框、>60 分点击直达审核页、10s 兜底轮询、高风险 Alert 横幅。

**问题：**
1. **🔴 WebSocket 地址疑似错误**：连的是 `/ws/live-wall`，而 Review 页用的是 `/api/v1/review/ws`，与 CLAUDE.md 约定的 `ws://host/ws/live-wall` 也对不上 vite 代理前缀——实时推送大概率从未连通，只剩轮询。
2. 🔴 两条 WS 都**没有断线重连**，onclose/onerror 全是空函数，网络抖动后电视墙静默死亡。
3. 🟡 新建直播间要求手填“推流密钥”，placeholder 却说“自动生成”——应该后端生成后展示可复制的 RTMP 地址（返回值里有 rtmp_push_url 但没用上）；content_id 是裸文本框而不是从内容列表选择。
4. 🟡 截帧快照依赖 onError 隐藏 img，失败后格子空白无文案；tile 上把置信度数字放在用户图标旁，含义不明。

### 第 9 步：质量抽检（QualityAudit.tsx）

**做得好：** 批次生命周期（草稿→进行中→完成）、双修正模式说明、进度条、抽检记录表 + 统计页签。

**问题：**
1. **🔴 抽检样本列表看不到内容本身**：样本条目只有元素类型 Tag + 风险分文字，没有图片/文本预览——质检员在不看内容的情况下打分，“抽检”失去意义。
2. **🔴 样本不是真抽样**：每次都现拉 `getPendingElements({ai_status})`，与批次无关，两个批次看到同样的“样本”；已抽检判断靠前端 `records.some(...)` 匹配。
3. 🟡 抽检发现误判后的“主动改判”联动（CLAUDE.md 宣称已实现）在前端没有任何入口——disagree 勾选后没有后续动作指引。

### 第 10 步：看板/日志/配置页

- **AuditLog**：筛选器存在但 `_setPage` 未接、表格 pagination 用默认配置与请求脱节；原因列显示英文枚举；无时间范围筛选、无导出。
- **TenantConfig**：规则表达式是自由文本 Input，没有语法说明/校验/测试工具——管理员写错了无从得知；敏感词/等级/规则三套 CRUD 结构雷同但均无批量导入。
- **AIConfig**：加载后把 apiKey 字段置空字符串，直接点保存可能用空串覆盖线上密钥（至少应区分“未修改”）；保存后无连通性测试按钮。

## 三、总评

**做得好的地方**：视觉体系统一（design tokens 单一来源）、审核工作台效率设计出色（快捷键/批量/分歧高亮/防机械误审）、aria-label 覆盖率高、空状态有引导文案、骨架屏与 loading 反馈完善。

**核心结论**：这个 demo 把“审核员工作台”打磨得像样，但作为“多租户 AI 审核平台”的三类用户旅程中，**创作者旅程基本不存在**（上传入口错位、无状态查询、申诉入口为零），**管理员旅程充满越权暴露**（全员可见租户增删），审核员旅程则埋着几个危险交互（Esc 秒打回、假“全部通过”、图片冒充视频播放）。建议优先级：

1. 🔴 打通申诉闭环：被打回内容处加“我要申诉”入口 + 创作者“我的内容/我的申诉”页 + 站内通知
2. 🔴 注册流程接入真实角色与租户关联；菜单与路由按 RBAC 过滤并给出 403 页
3. 🔴 修复短视频页三大 bug（视频源、全部通过、元素过滤）；统一快捷键与点击的安全确认层级
4. 🟡 修 WS 地址与重连、分页接线、枚举中文化
5. ⚪ 密码字段防覆盖、主题切换、批量上传
