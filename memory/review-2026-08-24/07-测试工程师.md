# 【资深测试工程师】Photo Audit Demo 字段级代码评审报告

> 范围：`backend/internal/{api,service,logger,middleware}` 全部生产代码 + 6 个测试文件（1139 行）+ 前端 `src/`（22 个文件，零测试）+ CI 配置。本机实测：`go vet ./...` 通过；`go test ./... -count=1` 通过；`go test -race ./...` 通过（但无 CI 门禁）；实测覆盖率 **api 0.4% / service 10.9% / logger 44.8%，其余包 0%**。

---

## 一、做得好的地方

1. **纯函数决策引擎可测性设计正确**：`TriggerContentDecision` 的核心判定逻辑是纯输入输出（elements → status），decision_test.go 用表驱动覆盖了 Phase 1/3/4/5 及权重边界（如 `TestTriggerContentDecision_CoverImageWeight` 精确验证了 2 > 4/2 为 false 的整数除法边界）。
2. **JWT 测试质量高**（auth_test.go）：正/负例齐全——过期 token、错误签名密钥、非法 token、平台管理员 nil tenant、24h 过期时间 `WithinDuration(…, 5s)` 断言。这是全项目最规范的一份测试。
3. **安全意识体现在代码与测试中**：SSRF 防护（`validateURL` 私有 IP 黑名单含 carrier-grade NAT 100.64/10、禁重定向、500MB LimitReader）、`DetectQuotaError` 对 402/429/关键词三分支有单测且断言了"非配额 500 返回 nil"的负例。
4. **fallback 降级链路有集成味道的测试**：空 API key → fallback 生效、quota error → fallback 触发，覆盖了 CLAUDE.md 正负例清单中的 AI 审核降级场景。
5. **handler 层防伪造字段处理正确并有注释**：`review_handlers.go:209/302/367` 三处均从 JWT 取 reviewer_id 而非请求体，注释明确标注 CRITICAL——这类安全不变量正是回归测试应该锁定的点。
6. **logger 测试通过注入 `bytes.Buffer` writer 验证 JSON 结构**而非只查子串，`TestLogger_LevelFiltering` 验证了行数过滤，隔离性好。

## 二、不好的地方（按严重度排序）

### 🔴 P0 — 决策引擎测试测的是"复印件"，不是生产代码
`decision_test.go:148-229` 的 `evaluateDecision()` 是把 `ingestion_service.go:429-550` 的 `TriggerContentDecision` **手工复制**出来的副本。文件注释自己承认："We can't easily construct IngestionService with mocked repos"。后果：
- 两个实现已经出现漂移：真实代码 Phase 4 在 `counted > 0` 时对**全部元素**求均值，副本一致，但真实代码 Phase 1 Rule 2 用的是标志位循环（`hasUnresolvedConflict`），副本用提前 return——行为目前相同，但任何一边改动另一边不会同步；
- **11 个 decision 测试全部给出虚假信心**：改坏生产代码里的 `>= 70` 或 `totalWeight/2`，测试依然全绿。

### 🔴 P0 — CI 完全不执行测试
`.github/workflows/ci.yml` backend job 只有 `go vet` + `go build`，**没有 `go test` 步骤**；frontend job 只有 `tsc --noEmit` + build。也就是说现有 1139 行测试在 CI 里从不运行，race detector 从未在门禁中执行。"测试通过"仅存在于开发者本机。

### 🔴 P0 — api 包测试全是 mock handler / 同义反复
- `handler_test.go` 7 个测试全部自建 `fiber.New()` 挂**内联闭包**，没有一条走 `SetupRoutes` 注册的真实路由（`TestHealthEndpoint` 测试的是测试自己写的 handler）。覆盖率实测 0.4% 即为证据。
- `TestBatchReviewRequest` / `TestReviewRequest` 是 `json.Marshal` 后立刻 `json.Unmarshal` 再断言——**同义反复**（tautology），验证的是标准库而不是业务 DTO，删掉不损失任何信息。
- `TestJWTTokenGeneration`（handler_test.go:119）与 auth_test.go 的 JWT 测试三重重复，且没校验签名方法（`jwt.Parse` keyfunc 直接返回密钥，不过滤 alg）。

### 🟠 P1 — 可测性设计的结构性缺陷：仓储层全是具体 struct，无接口
`ReviewService.elementRepo *repository.ElementRepository`、`IngestionService.contentRepo *repository.ContentRepository` 等（services.go、review_service.go:45-53）全部依赖具体类型。这直接导致：
- ingestion/review/appeal 三大核心服务**无法单测**（必须连真库）；
- 迫使团队复制粘贴决策逻辑来"绕过"不可测性（即 P0 第一条）；
- `NewServices` 是唯一组装点，`NewReviewService` 7 个位置参数、`ResolveAppeal` 事务横跨 3 个 repo——没有接口就没有 seam，事务回滚路径、并发冲突路径全部无法测试。

### 🟠 P1 — 已发现的疑似 bug（当前测试不可能抓到）

### 🟡 P2 — 测试质量问题（字段级）
1. **假断言**：`integration_test.go:88-95` simhash 相似度比较失败时只 `t.Log("skipping strict comparison")` —— 名为测试实为空转；`fingerprint_service_test.go:80-82` "不同图应产生不同指纹"也降级成 Log。
2. **永久 Skip 的死测试**：`integration_test.go:206-230` `TestConfigFallbackEnabled` 表驱动写完然后无条件 `t.Skip("envBool helper function not implemented")`——要么实现要么删除。
3. **重复**：simhash/hamming 测试同时存在于 `integration_test.go:71-111` 和 `fingerprint_service_test.go`，前者还是弱化版；`TestLocalFallbackServiceEndToEnd`（api/integration_test.go）与 `service.TestAIServiceFallbackIntegration` 几乎逐字重复，且放在 api 包里名不副实（不经过任何 HTTP 层）。
4. **弱断言**：`fingerprint_service_test.go:30` PerceptualHash 只 `t.Logf` 不断言非零/确定性；`FingerprintVideo` 出错即 `return`——错误分支永远不被验证。
5. **错误码契约不一致且被测试固化**：`TestAuthHandler_Login` 断言 HTTP 200 + body.code=401，而 review_handlers 大量使用真实 HTTP 状态码（404/409/403）。两种风格并存，前端无法统一处理；测试反而把反模式锁死了。
6. **JSON 解析错误被吞**：handler_test.go 多处 `json.Unmarshal(buf, &body)` 不检查 err（如 :30、:49），解析失败时断言的是零值碰巧相等的风险。
7. **middleware 包 0 测试**：`Tenant` 中间件（98 行，租户隔离的核心防线）无任何测试——X-Tenant-ID 缺失/非法 UUID/跨租户访问/platform_admin bypass 四条分支全部裸奔。B2 panic 就藏在这里。
8. **repository / config / storage / model 包 0 测试**：`user_repo.FindByUsername` 的 ErrNoRows 包装逻辑（auth_service.go:56 还要靠 `errors.Unwrap` 二段式解包，本身就很脆）无测试。

## 三、前端（一句话但重要）

`package.json` 无任何 test script、无 vitest/jest/testing-library 依赖。`services/api.ts` 的拦截器（token 注入、401 处理）、`stores/auth.ts`、`utils/format.ts` 都是纯逻辑，是最低成本的单测切入点。`Review.tsx` 762 行巨型组件（批量审核、筛选、WebSocket 刷新耦合在一起）既难测也是重构信号。

## 五、E2E 冒烟方案

分两层，都不需要 Kafka/ES（Phase 2/3 组件）：

**① 后端契约冒烟（Go 内置即可，进 CI）**
- 依赖：docker-compose 起 Postgres(+MinIO)，`cmd/migrate` 建库，真实 `pgxpool` 组装 `NewServices` + `SetupRoutes`。
- 冒烟脚本（一个 `_e2e_test.go`，build tag `e2e`）：注册租户管理员 → login 拿 JWT → 带 X-Tenant-ID 创建内容（title 含"违法"触发本地 fallback 得高分）→ 轮询 content 状态变为 rejected（Phase 4 AI 均值路径）→ 审核员 human reject → 断言 content=rejected + audit_log 有记录 → 提交申诉 → 二次申诉断言 409/拒绝 → resolve appeal=approved → 断言元素回到 pending_human + 收到 ConsoleNotifier 通知。
- 关键断言点正好覆盖 B1/B3/B5/B7 四个疑似 bug 的用户可见症状。

**② 前端 E2E（Playwright，本地手动/夜间跑）**
- `npm run dev` + 后端本地进程；3 条关键路径：登录 → Review 工作台卡片渲染与批量审核 → SubmitAppeal 表单提交成功提示；电视墙页在 WS 断连时的降级显示。暂不追求数量，先保证一条"上传→机审→人审→申诉"主干常绿。

## 六、优化与调整汇总

1. **架构调整**（解锁一切）：repository 接口化 → service 依赖注入接口 → 删除 decision 复印件。这是本仓库测试债务的根因，其余都是 symptom。
2. **统一错误响应契约**：全部走 RFC 7807 / 统一 `{code,message}` + 真实 HTTP 状态码，删掉 200+code 反模式，再写一个契约测试固化。
3. **合并双 ResolveAppeal 实现**（appeal_service.go:166 与 review_service.go:190），保留事务版。
4. **异步决策修 ctx**：B1 改 `context.WithoutCancel`；`c.Locals("tenant_id")` 全部加 ok 断言（B2 是线上可复现 panic）。
5. **CI 补齐**：`go test -race`、`gofmt -l` 检查、coverage badge；frontend 至少加 vitest + `@testing-library/react` 给 `api.ts`/`auth.ts`/`format.ts` 建立基线。
6. **清理测试卫生**：消灭所有"失败降级为 Log"的伪断言和永久 Skip；测试文件间去重（JWT×3、simhash×2、fallback e2e×2）。

---
**总结**：项目安全意识和纯函数抽取的意识值得肯定，race detector 本机可通过；但测试体系存在三个系统性问题——**决策逻辑测试测的是复制粘贴的副本、CI 根本不跑测试、api 层测试是 mock handler 自娱自乐**，导致核心链路（ingestion/review/appeal，约 1100 行）实际处于无保护状态，且已定位 7 处现有测试结构上不可能捕获的疑似 bug（其中 B1/B2 为可复现级）。本次为只读评审，未修改任何文件。
