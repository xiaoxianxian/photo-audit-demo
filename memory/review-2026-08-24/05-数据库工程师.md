## 一、做得好的地方

1. **CHECK 约束覆盖面广且规范**：`users.role`、`contents.content_type/status/review_policy`、`content_elements.element_kind/ai_status/human_status`、`appeals.status` 等枚举字段均有 CHECK。特别指出：**`element_kind` 实际上已有 CHECK 约束**（init.sql:317-318），任务背景中“element_kind 无 CHECK”的说法与代码不符——该问题已修复或不成立。
2. **业务唯一约束设计正确**：`uq_users_tenant_username (tenant_id, username)` 允许跨租户重名；`uq_appeals_content_applicant (content_id, applicant_id)` 支撑“一内容一申诉”规则；`uq_ai_configs_tenant` 保证每租户一份 AI 配置。
3. **扩展表模式清晰**：`contents` + 三张 `contents_*` 扩展表（PK 即 FK，ON DELETE CASCADE），主表查询轻量。
4. **索引有针对性**：`is_conflict` 用了部分索引 `WHERE is_conflict = true`；时间列统一 `DESC` 索引；外键列基本都有索引。
5. **SQL 细节到位**：`GetLatestSnapshots` 使用 `DISTINCT ON (stream_id)` 取每路直播最新帧；`GetDashboardStatsConsolidated` 把 8 个统计合并为单条 CTE + `COUNT(*) FILTER` 查询；排序字段全部走白名单防注入；动态 WHERE 全部参数化。
6. **乐观锁防重复改判**：`AppealRepository.UpdateWithTx` 带 `status NOT IN ('resolved_*')` 条件，0 行受影响返回 `ErrAppealAlreadyResolved`。
7. **主表+扩展表写入包事务**：`ContentRepository.Create` 中防止孤儿记录。

## 二、严重问题（Bug）

### B1. 分页参数错位 —— LIMIT 收到的是页码 ⚠️最高优先级
`element_repo.go:172`：
```go
rows, err := r.db.Query(ctx, listQ, append(args, page, pageSize*(page-1))...)
```
SQL 是 `LIMIT $idx OFFSET $idx+1`，但绑定顺序是 `(page, pageSize*(page-1))`。默认第 1 页时实际执行 `LIMIT 1`——**审核队列无论 pageSize 多大都只返回 1 行**。应为 `append(args, pageSize, (page-1)*pageSize)`。这是审核工作台核心路径的 P0 bug。

### B2. 排序白名单包含不存在的列
`content_repo.go:102`：`allowedSortCols` 含 `"title"`，但 `title` 在扩展表 `contents_photo` 等，不在 `contents` 上，用户传 `sort_by=title` 直接 SQL 报错（500）。

### B3. 扩展表数据查了又扔（死代码）
`content_repo.go:330-366`：`readPhotoRow/readShortVideoRow/readLiveStreamRow` 把 title/original_url 等扫描进局部变量后丢弃，返回的 `*model.Content` 不含任何扩展字段——白做一次查询，调用方拿不到标题/URL。要么映射进模型，要么删掉。

### B4. 事务内使用 `context.Background()` 丢失取消语义
`content_repo.go:290/308/326`：三个 `create*RowTx` 在 `Create(ctx)` 的事务里用 `context.Background()` 执行 Exec——请求超时/客户端断开不会传播，事务可能悬挂占用连接池。

### B5. `tenant_audit_levels.level_code` 全局唯一，租户互相冲突
init.sql:221：`level_code VARCHAR(32) NOT NULL UNIQUE`。租户 A 定义了 `level_code='ban'` 后租户 B 无法定义同名等级。应改为 `UNIQUE (tenant_id, level_code)`。

### B6. 设计文档承诺的能力未落地（核实结果）
| 文档声明 | 实际情况 |
|---|---|
| audit_records / audit_logs 按月分区 | **完全未落地**，两张表都是普通堆表 |
| audit_logs 表（operator_id 操作日志） | **表不存在**，`tenant_service.go:63/154` 只有 TODO 注释 |
| audit_tasks 任务表（assignee_id） | **表不存在**，导致 `audit_records.task_id` 只能用零值 UUID 兜底（见 D1） |
| 数据库层 RLS 租户过滤 | **无任何 RLS 策略/POLICY**，隔离全靠应用层 |

### B7. 租户隔离在数据层多处漏防（无 RLS 的直接后果）
以下查询**完全没有 tenant 过滤**，租户 A 的用户可看到租户 B 的数据（middleware 只校验 Header 合法性，不强制注入 WHERE）：
- `ElementRepository.FindByStatus` / `CountByFilters`（审核工作台队列与统计条！签名中根本没有 tenant 参数）
- `UserRepository.List` / `FindByUsername`（后者跨租户全局查找，配合 (tenant_id, username) 可重复名，登录解析有歧义）
- `AppealRepository.ListByStatus`
- `LogRepository.ListAllFiltered`

建议：要么真正启用 RLS（`SET app.tenant_id` + POLICY），要么所有仓储方法强制接收 tenantID 并在代码评审中设为门禁项。

### B8. `cmd/migrate` 健壮性问题
- `migrateUp`/`status`：`pool.Query` 出错时 `err` 被吞掉、`applied` 保持 nil → **静默重新执行全部迁移**；且 rows 未 Close（连接泄漏）。
- 迁移文件执行与版本记录不在同一事务：exec 成功、INSERT schema_migrations 失败会造成状态不一致。
- 无 advisory lock（`pg_advisory_lock`），并发部署会竞争。
- `status()` 里 `rows.Scan` 错误被忽略。

## 四、查询性能

1. **N+1 少，但重复计数多**：`ElementRepository.CountByFilters` 对同一批过滤条件发 3~4 条独立 `COUNT(*)` 全表扫；可合并为一条 `COUNT(*) FILTER (WHERE human_status=…)` 条件聚合（dashboard 已示范了该写法）。
2. **OFFSET 深分页**：audit_records/elements 列表均用 LIMIT/OFFSET，大偏移下性能塌陷；append-only 的 audit_records 很适合 keyset 分页（`WHERE created_at < $last ORDER BY created_at DESC LIMIT n`）。
3. **`GetLatestSnapshots`**：DISTINCT ON 最优索引是复合 `(stream_id, snapshot_time DESC)`，当前是两个独立索引，需回表排序。
4. **租户 JOIN 统计链**：`c.tenant_id = $1 AND ar.created_at >= …` 先从 contents 过滤再 JOIN 是对的方向，但没有 S1 的冗余 tenant_id 时优化器选择受限。
5. **死代码**：`QualityAuditRepository.GetUnreviewedElementsForBatch` 组装完 reviewedIDs 后 `_ = reviewedIDs; return nil, nil`，永远返回空；`createPhotoRow/createShortVideoRow/createLiveStreamRow` 非 Tx 版本无人调用——建议删除。

## 五、迁移策略：双轨制评估（cmd/migrate vs init.sql）

- **漂移已发生**：init.sql 有种子数据 + 内联 `ALTER TABLE ... ADD CONSTRAINT fk_tenants_created_by_users`；001_up.sql 用 `DO $$ ... EXCEPTION WHEN duplicate_object` 幂等块、**无种子数据**。两条路径建出的库内容不同。
- init.sql 用 `BEGIN/COMMIT` 包裹整体（好），但没有 `IF NOT EXISTS`，先跑 migrate 再跑 init.sql 必然失败；反之亦然。
- **建议收敛为单一事实源**：保留 migrations 为权威，init.sql 改为“001_up.sql + seed.sql”的生成产物（CI 校验一致性），或在 README 明确 init.sql 仅用于 demo 一键起库、禁止在其上增量演化。`cmd/migrate` 需修 B8 并补事务化与锁。

## 六、结论摘要

- **P0（立即修）**：B1 分页 LIMIT 参数错位；B7 审核队列/统计条无租户过滤；B5 level_code 全局唯一冲突。
- **P1**：B2/B3/B4 仓储层缺陷、B6 分区与 audit_logs/audit_tasks 未落地（需决策：实现或从文档删除）、B8 migrate 工具健壮性、S1 audit_records 冗余 tenant_id。
- **P2**：S2/S3 索引与物化视图、S4-S9 约束补齐、双轨迁移收敛、OFFSET→keyset 分页。
- 正面评价：CHECK 约束体系、部分索引、DISTINCT ON、合并式 dashboard CTE、乐观锁等细节体现了不错的 PG 功底；主要短板集中在**文档承诺与实现的偏差**以及**租户隔离没有下沉到数据层**这两点。
