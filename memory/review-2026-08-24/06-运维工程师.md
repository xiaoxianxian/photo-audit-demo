## 二、Bug（会实际出问题的字段级缺陷）🐞

### B1. `DATABASE_URL` 中密码是字面量 `***` —— 密钥轮换后全链路断连
出现在 **5 处**：`backend/.env.example:6`、`generate-secrets.sh:38`（把 `***` 写进生成的 .env！）、`docker-compose.full.yml:84`、`photo-audit.service:11`、`start-local.sh:77`。
而 postgres 实际密码来自 `${POSTGRES_PASSWORD:-postgres}`。一旦按脚本指引设置了强密码，后端将永远无法认证。`docker-compose.full.yml:84` 应为：
```yaml
DATABASE_URL: postgresql://postgres:${POSTGRES_PASSWORD}@postgres:5432/photo_audit?sslmode=disable
```
目前"能跑通"纯粹依赖本地 trust 认证或默认弱密码——**这是部署配置里最核心的字段级 bug**。

### B2. `JWTMinLength` 校验完全失效
`config.go:47`：``JWTMinLength int `mapstructure:"JWT_MIN_LENGTH" default:"32"` `` —— 该结构体没有 mapstructure 反射加载逻辑，`defaults` map 里也没有 `JWT_MIN_LENGTH`，此字段永远是零值 `0`。于是 `main.go` 的 `len(cfg.JWTSecret) < cfg.JWTMinLength` 永远为 false，`.env.example` 里"MUST be at least 32 characters"的承诺没有任何代码兜底。

### B3. `photo-audit.service` 自带自杀性默认值
- L12 `Environment=JWT_SECRET=change-me-in-production`（23 字符）：即使 B2 修好，这个硬编码值也会**覆盖环境里配置的真密钥**，且长度不足直接被 main.go Fatal；systemd 的 `Environment=` 优先级高于 `EnvironmentFile`。
- L16 `ExecReload=/bin/kill -HUP $MAINPID`：Go 程序只捕获 SIGINT/SIGTERM，`systemctl reload` 会直接杀死进程。
- L19-20：`StartLimitInterval`/`StartLimitBurst` 写在 `[Service]` 段，现代 systemd 要求放 `[Unit]` 段，否则不生效（无限重启风暴防护失效）。

### B4. 双守护体系冲突
`deploy-native.sh`/README 引导用 systemd，同时又提供 `photo-audit-monitor.sh guard`。若两者同时运行，两个监督者会互相抢拉起同一个二进制（PID 文件 vs systemd 的 cgroup 各自为政）。且守护脚本达到 MAX_RESTARTS 后 `exit 1` 彻底放弃、无任何告警通道——比 systemd 更差的可用性。

### B5. `deploy-native.sh:104-108` 每次执行都 DROP DATABASE
```bash
psql ... -c "DROP DATABASE IF EXISTS photo_audit;"
createdb ...
```
一个"部署脚本"无条件删库，在任何已有数据的环境跑一次就是生产事故。必须加显式 `--fresh` 开关或存在性确认。同文件 L126 往 `pg_hba.conf` 追加 `trust` 认证规则，属于安全降级。

### B6. 日志压缩函数名不符实
`logger.go:130-137` `compressLogFile` 只是把文件改名成 `.gz` 后缀，**并没有 gzip 压缩**，且轮转只在进程启动时检查一次文件大小——长期运行的进程日志无限增长；也没有旧轮转文件的保留上限清理。另外 `main.go:74-76` 把"LOG_FILE 未设置"强行默认成 `logs/audit-platform.log`，与 `.env.example:39-40` "Optional: enable file logging" 的语义矛盾（想纯 stderr 输出做不到，容器里会白写一份文件层）。

### B7. Redis 健康检查密码泄漏面
`docker-compose.yml:38`：`redis-cli -a ${REDIS_PASSWORD} ping` —— 密码进入容器内 `ps` 输出和 redis-cli 的 warning 日志。应改用 `redis-cli ping` + `REDISCLI_AUTH` 环境变量，或 `CMD-SHELL` 方式。

### B8. `start-local.sh` 就绪检测逻辑失效风险
L107 `lsof -i :8080 || ss -tlnp | grep 8080` 在 macOS 上无 `ss`，`lsof` 失败时循环空转 60 秒；且后端若启动即崩溃，循环不会提前退出报错。L97 `./audit-server &` 后脚本以 `wait` 结尾，Ctrl-C 时前端 vite 进程可能残留（stop-local.sh 靠 `pkill -f vite` 兜底过于粗暴，会误杀其他项目的 vite）。

## 三、不好的地方（设计层面）⚠️

### 容器化质量
1. **`Dockerfile.frontend` 是"伪生产"镜像**：名为 builder 实为 Vite dev server（`npm run dev --host`），`deploy-local.sh` 却把它当部署产物。生产应 `npm ci && npm run build` + nginx 多阶段输出静态文件。dev server 单线程、内存占用高、无 gzip/缓存策略，根本不可扩容。
2. `npm install` 应为 `npm ci`（锁文件确定性）；frontend 镜像无 HEALTHCHECK。
3. `Dockerfile.backend` 最终镜像 **以 root 运行**（缺 `USER`），未装 tzdata（`TimeZone: Asia/Shanghai` 依赖它却没装），无 `-ldflags "-s -w"`/版本号注入，无 `HEALTHCHECK` 指令。`.dockerignore` 缺 `*.db`（`backend/photo_audit.db` 会进构建上下文）和 `*.md`。
4. 所有 compose 服务缺 `restart: unless-stopped`；`version: "3.8"` 字段已废弃可删。
5. **端口全部绑定 `0.0.0.0`**：5432/6379/9000/9001 对外网裸奔，应改 `127.0.0.1:5432:5432` 或删除（走内部网络）。
6. `x-common-vars` 把整个 `.env.development` 注入 postgres/redis/minio 容器 —— `JWT_SECRET` 等无关密钥可通过 `docker inspect` 读到，属于密钥扩散面问题。
7. 镜像标签 `minio/minio:latest` 不可复现部署。

### 环境隔离
8. **没有 dev/prod 分离**：只有 `.env.development` 一个模板，`ALLOWED_ORIGINS` 代码默认 `*`（已知问题）、`sslmode=disable` 全线使用、`MIGRATE_AUTO_UP` 在 deploy-native.sh 里 true 而 example 里 false（行为不一致）。缺少 `.env.production.example` 与 prod compose overlay（如 `docker-compose.prod.yml`）。
9. `JWT_SECRET` 未设时自动随机生成（已知问题）：单机重启全员掉线、多副本 token 互不认账——运维角度这是**水平扩容的硬阻断项**，应在非 dev 环境 fail-fast。

### 日志与监控
10. Fiber 访问日志是人读格式（`${ip} ${method} ...`），与应用 JSON 日志两套格式并存，采集端要写两种解析器。
11. **无任何指标暴露**：没有 `/metrics`（Prometheus）、没有 AI 调用成功率/队列深度/审核延迟等业务指标，monitor 脚本只看进程存活不看端口/健康接口（`is_running` 仅 `kill -0`，僵死进程照样认为健康）。
12. `monitor.log`、`server.log` 无轮转；`logs()` 直接 `tail -f` 无分页保护。

### 备份恢复
13. **全项目零备份方案**：无 pg_dump 定时任务、无 MinIO 数据备份、无 restore 演练文档、README/DEPLOYMENT 文档中 grep 不到"备份"。pg_data/redis_data/minio_data 全在本地 named volume，一次 `down -v` 手滑即全部蒸发。审核记录属合规敏感数据，这是最高优先级缺口。

### 扩容能力
14. 单机 compose 架构：限流器内存态 per-instance、WebSocket hub 内存态（多副本时电视墙推送错乱）、SQLite 残留（`backend/photo_audit.db`）暗示双持久化混乱、随机 JWT_SECRET 阻断多实例。当前形态只能垂直扩容。
15. 限流 `Max:100 / 15min` 全局写死不可配：批量上传图片场景自己就会触发 429，反代后所有用户共享代理 IP 一个桶。

## 四、可优化建议（按优先级）🔧

**P0（上线阻断）**
1. 修 `DATABASE_URL` 的 `***` 占位（B1，5 处）；
2. 删除 systemd unit 内嵌的 `JWT_SECRET`/`DATABASE_URL`，改 `EnvironmentFile=/opt/photo-audit/.env`（权限 600、www-data 可读）；修 `StartLimit*` 到 `[Unit]` 段、去掉 HUP reload；
3. `deploy-native.sh` 的 DROP DATABASE 加守卫；
4. 补备份：`pg_dump` cron + MinIO `mc mirror` + 恢复文档与演练记录；
5. 生产前端改为静态构建 + nginx（或至少 Caddy），dev server 只留 dev。

**P1**
6. 二选一进程守护：只用 systemd（推荐），monitor.sh 降级为开发工具或删除，避免双监督；
7. 非 dev 环境下 `JWT_SECRET` 缺失应拒绝启动而非静默生成；同时修复 `JWTMinLength` 使 `JWT_MIN_LENGTH` 真正可配（并入 `defaults` map）；
8. compose 收敛端口绑定到 127.0.0.1、补 `restart: unless-stopped`、拆掉 `x-common-vars` 全量注入、Redis 健康检查改 `REDISCLI_AUTH`；
9. Dockerfile.backend 加非 root USER、HEALTHCHECK（指向 `/api/v1/live`）、版本 ldflags；compose 健康检查从 `/api/v1/health`（静态假活）换成 `/api/v1/ready`（真查依赖）；
10. 日志统一 JSON（Fiber middleware 换成结构化 logger 或引入 slog/zap + request ID），LOG_FILE 默认改空、轮转改为定期检查 + 保留 N 份。

**P2**
11. 增加 `docker-compose.prod.yml` overlay + `.env.production.example`（强密码校验、CORS 白名单、TLS 终结层 nginx/Traefik、`sslmode=require`）；
12. 暴露 `/metrics`（Prometheus），监控脚本升级为探活 `/api/v1/ready` + 告警通知（webhook/邮件）；
13. 限流参数环境变量化并区分登录/上传/API 路径；反代场景 `EnableTrustedProxy` 修正 `c.IP()`；
14. 镜像 tag 固定 + 私有 registry；为扩容预留：JWT 共享密钥（已具备条件）、限流迁 Redis、WebSocket hub 改 Redis pub/sub；
15. 清理仓库里的 `backend/photo_audit.db`、`frontend/vite.config.ts.timestamp-*` 等构建垃圾。

## 五、总结

工程意识和骨架不错（健康检查三件套、优雅停机、多阶段构建、密钥生成脚本都在），但**当前部署物不能安全上生产**：核心连接串密码占位符 `***` 贯穿 5 个文件、systemd unit 内嵌危险默认密钥、原生部署脚本无条件删库、零备份体系、前端以 dev server 冒充生产镜像。P0 五项修完之前，建议此项目仅停留在 demo 定位。
