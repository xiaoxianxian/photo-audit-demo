## 二、不好的地方（结构性）

1. **依赖注入模式混乱：构造函数 + `With*` setter 混用**。`AIService` 有 `WithFallback`/`WithAIConfigRepo`，`IngestionService` 有 `WithVideoProcessor`/`WithHub`，全仓 14 处 setter。这造成 *temporal coupling*——忘了调 setter 就是运行期 nil panic，而不是编译期错误；且迫使所有使用点散布 `if s.xxx != nil` 判空（`ingestion_service.go:315/409`、`review_service.go:134` 等）。setter 应收敛进构造函数或拆出 options struct。

2. **依赖全是具体类型，零接口**。除 `Notifier` 外，repo 和 service 字段都是 `*repository.XxxRepository` 具体指针。后果：(a) 单测必须真连 PG（现仅 integration_test 覆盖）；(b) Phase 2 拆微服务时无法在不改调用方的情况下替换本地实现为 RPC client。

3. **服务边界渗漏**：
   - `Handlers` 构造里直接摸内部字段：`h.elementRepo = svc.ElementRepo`、`NewContentHandlerWithStorage(svc.IngestionService, svc.ContentRepo, svc.MinIO)` —— ContentHandler 同时拿到 service 和两个 repo，绕过分层；
   - `AIService.GetAIConfigs/maskAPIKey`（ai_service.go:383-413）是租户配置管理职责，混进了 AI 调用服务；
   - `LiveWallService.streamRepo` 被 `StreamScheduler` 跨层直取（`s.liveSvc.streamRepo.GetActiveStreams`），scheduler 应依赖自己的 repo 接口。

4. **异步链路无持久化**。AI 审核触发靠 `go h.ingestionSvc.TriggerAIReview(...)` 裸 goroutine：进程重启即丢任务，无重试队列、无 outbox。CLAUDE.md 自己也标注“goroutine 异步触发 AI review，非 Kafka”。这是 Demo 可接受、上生产必炸的第一优先级债务。

5. **文档与实现不符（RLS）**。CLAUDE.md 称“数据库层通过 RLS 过滤”，但全仓无任何 `CREATE POLICY` / `SET LOCAL row_security`，隔离完全依赖 repo 查询自觉带 tenant_id 条件——一旦某个查询漏加即跨租户泄漏。

## 三、Bug（按严重度排序）

1. **🔴 `c.Context()` 传入后台 goroutine（数据竞争/UB）**
   `content_handlers.go:164/513`：`go h.ingestionSvc.TriggerAIReview(c.Context(), ...)`；`review_service.go:135-139` 同样把请求 ctx 捕获进 goroutine 调 `TriggerContentDecision`。Fiber/fasthttp 的 `RequestCtx` 在 handler 返回后被池化复用，goroutine 稍后用它查库会读到脏数据或 panic。**修法**：handler 内 `context.WithoutCancel(c.UserContext())` 或新建 `context.Background()` 传入。

2. **🔴 judge 解析失败静默返回 0 分 → 必然误判分歧**
   `parseJudgeResponse`（ai_service.go:377-378）找不到 score 时 `return 0, nil`。随后 `diff = primary − 0`，只要主审 >20 分就误标 `IsConflict=true`，污染整个决策引擎（Rule 2 强制 `in_human_review`）。应 `return 0, errors.New("no score in judge response")`。

3. **🟠 `UpdateStatus` 双列无条件覆盖 → 状态互踩竞态**
   `element_repo.go:194` 的 `UPDATE ... SET ai_status=$1, human_status=$2` 要求调用方同时提供两列当前值。`HumanReview` 传入的是读取时刻的 `elem.AIStatus` 快照——若此刻 `TriggerAIReview` 正在并发推进状态，人审会把 AI 状态写回旧值（反之亦然）。**修法**：拆成独立列更新，或 `WHERE ai_status=$expected` 乐观锁。

4. **🟠 `HumanReview` 两步写无事务**：`AuditLogRepo.Create`（review_service.go:121）成功后 `elementRepo.UpdateStatus` 失败 → 审核记录已落库但元素状态未变，统计与实际状态永久漂移。已有 `BeginTx/CreateWithTx` 设施却没用在这里。

5. **🟠 `ResolveAppeal` 改判后内容级状态不重算**：approved 分支把元素回滚到 `pending_human`（review_service.go:258-265），但从不调用 `TriggerContentDecision`，contents.status 仍停留在 "rejected" —— 内容状态与其元素状态不一致。

6. **🟡 `audit_record.ElementID` 写入了 ContentID**：review_service.go:238 `ElementID: appeal.ContentID`，字段语义错误，会污染按 element 维度的报表与追溯。

7. **🟡 `ctx.Value("user_id")` 永远取不到**：review_service.go:223 从标准 context 取值，但 auth 中间件写在 Fiber `c.Locals`，这段 fallback 是死代码，掩盖了 reviewerID 缺失时应报错的事实。

8. **🟡 `Hub.Run()` 无退出通道**：`websocket_hub.go:125-146` 的 for-select 没有 stop case，`Stop()` 只清连接不结束 goroutine；`stopCh` 模式在 StreamScheduler 里已有，Hub 应复用。

9. **🟡 WS close/send 竞态**：广播在持 `h.mu.Lock()` 下 `close(client.send)`，而 `WritePump` 的 `<-c.send` 未检查 `ok`——channel 关闭后读到 nil message 继续执行 `WriteMessage(TextMessage, nil)` 而非退出。

10. **🟡 StreamScheduler 造假数据入库**：`captureSnapshot` 用 `streamRng.Intn(30)` 生成"AI 风险分”写进 live_wall 快照表并推给电视墙——演示数据与真实审计数据同表存储，无来源标记字段区分。另外 `markStreamOffline` 对 `s.wsHub` 无 nil-check，`streamJob.interval` 字段赋值后从未使用，`isStreamHealthy` 对每个 job 全量拉 active streams（N×M 查询）。

11. **🟡 杂项**：`TriggerAIReview` 把 `Reason` 字符串塞进 `risk_types` 数组（语义错位）、confidence 硬编码 0.9 丢弃模型真实置信度（ingestion_service.go:364-369）；`BatchReview` 逐条提交非原子、fail-fast 留下半成品批次且每条各起一个 decision goroutine；全局限流 100 次/15 分钟/IP 对审核工作台轮询场景明显偏紧；MinIO 初始化失败用裸 `fmt.Println` 而非结构化 logger（services.go:139）。

## 四、已知问题的确认与深评

**① IngestionService 6 个依赖字段**（`contentRepo/elementRepo/aiSvc/videoProc/wsHub/contentMu`）— 属实。它实际承担了：内容创建、视频预处理编排、SSRF 防护、AI 审核调度、裁判协调、内容级裁决引擎、WS 通知七种职责，是全仓最大的上帝类苗头（550 行还在涨）。其中 `validateURL/isPrivateIP` 是纯函数，应下沉到 `pkg/` 或独立 safety 包；`TriggerContentDecision` 决策引擎（~120 行纯逻辑）应拆为 `DecisionEngine`，它是全仓最值得抽接口做单测的部分（现有 decision_test 已证明其可测性红利）。

**② `contentMu sync.Map` 做 per-content 锁** — 能用，但有三个问题：
- **内存泄漏**：entry 只增不删，每个历史 content 永久占一个 mutex；应审完 `Delete(contentID)`（需小心 double-check 模式）或改用分片锁固定上限；
- **仅进程内有效**：多实例部署下锁失效，真正的并发防线应是 DB 层（`SELECT FOR UPDATE` / 乐观版本号）；
- 锁内做两次 DB 往返（FindByContentID + UpdateStatus），持锁时间不可控。
结论：Demo 合格，多实例前必须替换为数据库级串行化。

**③ AIService 职责混杂** — 属实，见上文三-3。建议拆为：`agnes.Client`（HTTP+解析）、`judge.Client`（DeepSeek）、`QuotaPolicy`（降级判断）、配置管理归还 `TenantConfigService`；`os.Getenv("AGNES_API_ENDPOINT")` 直读环境变量应改为 config 注入；DeepSeek URL 硬编码（ai_service.go:218）应进配置。

**④ WS Hub 无背压** — 属实且比"无背压”更糟：256 buffer 满时**直接杀连接**（close+delete），高峰期慢客户端会被批量踢线造成重连风暴；且持全局写锁遍历所有连接做发送，一个慢 send 会阻塞其他租户的广播。改进路线：per-client 独立 writer goroutine + 消息合并（电视墙快照只需最新一帧，可 drop-stale）+ 断开改为标记由 ReadPump 统一清理。

## 五、可优化项

- `TriggerAIReview` 结尾的通知 goroutine 用 `CountByFilters(..., 0, 100)` 统计 pending 数——limit=100 意味着超过 100 条时报数失真，应改用 COUNT 专用方法；
- `getDB`（main.go:37-62）：初始化失败后 `dbPool=nil, err≠0` 被闭包捕获，但 `dbOnce` 已消费，若未来有第二次调用会返回 `(nil, 旧err)`；建议失败即 Fatal；
- migration 目录定位靠 `"../../.."` 相对 cwd 推算（main.go:236），换工作目录即崩，应 embed 或绝对路径配置；
- `weightedElement.aiRisk` 字段收集后从未使用（ingestion_service.go:472）；Phase 4 平均风险把已被人工**通过**的元素也算进去，且整数除法截断、阈值 60/70 全部硬编码——决策参数应配置化为租户级规则（tenant_audit_rules 表已有，未接入）；
- `Services` 结构体导出了 `ReviewService.AuditLogRepo`、`ReviewService.WSHub` 公有字段，破坏封装统一性。

## 六、Phase 2 微服务拆分路径建议

当前单体边界其实已隐约成形，按依赖图拆分阻力最小：

1. **先立端口（最高优先，一切的前提）**：为 `ElementRepository/ContentRepository/AIService/Notifier` 定义接口，service 层只依赖接口——否则拆出的每个服务都要带着 pgxpool；
2. **ingestion-service**：上传 + 元素拆分 + VideoProcessor + SSRF 校验，产出“内容已接入"事件；
3. **ai-review-service**：AIService + LocalFallback + DecisionEngine，从事件队列消费（引入 Kafka 或先用 PG `SKIP LOCKED` 任务表过渡），替代裸 goroutine + outbox 补齐可靠性；
4. **notification-service**：Hub + StreamScheduler + Notifier，WS 网关独立部署，跨实例广播走 Redis pub/sub（当前 `connections map` 天然单机）；
5. **留在核心的**：review/appeal/quality（强事务、共享 schema，最后拆甚至不拆）；
6. **前置硬条件**：把 CLAUDE.md 承诺的 RLS 真正落地，否则拆开后跨服务查询将失去最后一道租户防线。
