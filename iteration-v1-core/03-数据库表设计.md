# 03-数据库表设计（v2：供稿 + 直播 + 短视频 + 多租户）

## 设计原则

1. **租户隔离**：所有业务表带 `tenant_id`，通过 PostgreSQL Row Level Security (RLS) 实现数据隔离
2. **append-only**：审核记录不可修改，只追加新记录；改判通过新记录体现
3. **元素拆分**：内容按类型拆分为独立元素，每个元素独立走审核流程
4. **分区表**：审核记录、日志等大表按时间分区（月度分区）

#### 9. content_elements（内容元素表 — 核心枢纽）

> **每个内容进来后，按类型拆成多条元素记录，每条独立走 AI 和人审流程。这是整个审核链路的核心表。**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | UUID PK | 元素 ID |
| content_id | UUID → contents.id | 父内容 ID |
| element_type | varchar(32) | cover_image / video_frame / title / comment / asr_text / user_avatar / nickname / description |
| element_content | text | 文本原文或 MinIO URL |
| ai_risk_score | smallint | AI 风险分（0-100） |
| ai_risk_types | jsonb | 风险类型列表（如 `["porn","violence"]`） |
| ai_confidence | numeric(3,2) | AI 置信度（0.00-1.00） |
| ai_status | varchar(32) | pending_ai / ai_processing / ai_passed / ai_rejected |
| human_status | varchar(32) | pending_human / in_human_review / human_passed / human_rejected |
| is_conflict | boolean | 是否与裁判模型结论分歧 |
| created_at | timestamptz | 创建时间 |

**索引：** `(content_id, ai_status, human_status)` 复合索引，加速待审队列查询。

## 表关系总结（ER 文字版）

```
tenants (1)
  ├─ (N) users (tenant_id)          ← 用户归属租户
  ├─ (N) audit_teams (tenant_id)    ← 审核团队
  ├─ (N) contents (tenant_id)       ← 所有内容
  ├─ (N) tenant_audit_rules
  ├─ (N) tenant_custom_words
  ├─ (N) tenant_audit_levels
  └─ (N) sampling_tasks

users (1)
  ├─ (N) contents (creator_id)      ← 创作者
  ├─ (N) audit_teams (leader_id)    ← 团队负责人
  ├─ (N) audit_team_members (user_id) ← 团队成员
  ├─ (N) audit_records (reviewer_id) ← 审核记录
  ├─ (N) audit_tasks (assignee_id)   ← 分配的任务
  ├─ (N) appeals (applicant_id)     ← 申诉人
  └─ (N) audit_logs (operator_id)

contents (1)
  ├─ (1) contents_photo
  ├─ (1) contents_short_video
  ├─ (1) contents_live_stream
  └─ (N) content_elements            ← 核心：内容拆分为元素

content_elements (1)
  ├─ (N) audit_tasks                 ← 每个元素产生审核任务
  └─ (N) audit_records               ← 审核结果记录

contents_live_stream (1)
  └─ (N) live_frame_snapshots        ← 直播截帧

appeals (1)
  └─ (N) appeal_notifications        ← 申诉通知

quality_check_batches (1)
  └─ (N) quality_check_items
```

## 索引策略要点

1. **content_elements**: `(content_id, ai_status, human_status)` 复合索引 — 加速待审队列查询
2. **audit_records**: 按月分区 + `(element_id, created_at)` — 加速按元素追溯
3. **audit_tasks**: `(element_id, task_type, status)` — 加速任务分配
4. **contents**: `(tenant_id, content_type, status, created_at)` — 加速租户维度的内容检索
5. **live_frame_snapshots**: `(content_id, snapshot_time)` DESC — 加速电视墙最新帧查询
6. **audit_logs**: 按月分区 — 控制单表大小，提升查询性能
