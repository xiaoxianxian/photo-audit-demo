# 05-存储方案与架构升级说明

## 一、对象存储方案：MinIO

### 为什么选 MinIO

1. **自建可控**：数据不出内网，符合审核平台合规要求
2. **S3 兼容**：代码层面只需改 endpoint 就能切到阿里云 OSS / AWS S3
3. **轻量部署**：单二进制文件，资源占用极低
4. **多租户隔离**：MinIO 支持 bucket 级别的租户隔离

### 存储结构

```
minio/
├── {tenant_id}/
│   ├── photos/
│   │   ├── {content_id}/
│   │   │   ├── original/      # 原图
│   │   │   └── thumbnail/     # 缩略图（256px 宽）
│   │
│   ├── videos/
│   │   ├── {content_id}/
│   │   │   ├── original/      # 原视频
│   │   │   ├── thumbnail/     # 封面帧
│   │   │   └── frames/        # 抽帧图片（每 N 秒一帧）
│   │
│   ├── lives/
│   │   ├── {content_id}/
│   │   │   └── snapshots/     # 截帧快照（每 15s 一帧）
│   │
│   ├── appeals/
│   │   └── {appeal_id}/       # 申诉证明材料
│   │
│   └── reviews/
│       └── {content_id}/      # 审核快照（操作时的界面截图）
```

### CDN 策略

- **走 CDN**：缩略图、封面帧（读多写少，静态资源）
- **不走 CDN**：原图、原视频、截帧原图（敏感内容，仅内网访问）

## 二、千万级日处理量的架构挑战

### 数据量估算

| 项目 | 日处理量 | 月数据量 | 年数据量 |
|------|---------|---------|---------|
| 供稿图片 | 1000 万 | 3 亿 | 36 亿 |
| 短视频 | 100 万 | 3000 万 | 3.6 亿 |
| 直播截帧（假设 500 路 × 24h × 1 帧/15s） | 约 8640 万 | 26 亿 | 310 亿 |
| AI 审核调用 | ~1 亿 | ~30 亿 | ~360 亿 |
| 审核记录 | ~5000 万 | ~15 亿 | ~180 亿 |

> 注：直播截帧量最大，是主要压力源。

### 架构分层

```
┌─────────────────────────────────────────────────┐
│                   前端 (React)                    │
│   审核工作台 │ 电视墙 │ 申诉 │ 管理后台            │
└──────────────────┬──────────────────────────────┘
                   │ HTTPS / WebSocket
┌──────────────────▼──────────────────────────────┐
│              API Gateway (Nginx/Kong)             │
│         限流 │ 鉴权 │ 路由 │ 日志                 │
└──┬────────────┬────────────┬────────────┬────────┘
   │            │            │            │
   ▼            ▼            ▼            ▼
┌──────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│内容接入│  │ AI调度  │  │ 审核工作台│  │ 租户管理  │
│服务   │  │ 服务     │  │ 服务     │  │ 服务      │
└──┬───┘  └────┬─────┘  └────┬─────┘  └────┬─────┘
   │           │             │             │
   ▼           ▼             ▼             ▼
┌──────┐  ┌──────┐    ┌──────┐    ┌──────┐
│ Kafka │  │Redis │    │PG(主) │    │ PG   │
│ 消息队列│ │缓存  │    │读写分离│    │ R/W   │
└──────┘  └──────┘    └──────┘    └──────┘
   │
   ▼
┌──────────┐    ┌──────────┐
│AI 服务集群 │    │ MinIO    │
│Gemini/GPT │    │ 对象存储  │
│ASR/NLP    │    │          │
└──────────┘    └──────────┘
```

### 关键技术决策

1. **异步队列（Kafka）**：内容接入不阻塞，审核任务排队处理
2. **读写分离**：PG 主从复制，审核工作台读从库
3. **Redis 缓存**：
   - 电视墙实时状态（毫秒级刷新）
   - 用户会话
   - 热点内容缓存
4. **PG 分区表**：audit_records、audit_logs 按月分区
5. **ES 搜索引擎**：审核记录全文检索、运营报表多维查询

## 三、直播实时审核的特殊架构

### 直播审核链路

```
推流(RTMP) → 转码(HLS) → 截帧服务(每15s) → 图片上传MinIO
                                                    ↓
                                            AI 视觉审核(Gemini)
                                                    ↓
                                            风险分写入 Redis(实时)
                                                    ↓
                                            WebSocket 推送到电视墙
```

### 电视墙技术要点

- 每路直播的状态存在 Redis Hash 中
- 前端 WebSocket 订阅 `live:{streamer_id}` 频道
- 截帧 AI 审核结果写入 Redis → 触发 WebSocket 推送
- 延迟目标：< 3 秒（截帧到电视墙刷新）
