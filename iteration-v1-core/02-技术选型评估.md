# 02-技术选型评估（v2：千万级日处理量）

## 评估维度（已更新）

| 维度 | 说明 |
|------|------|
| **日均处理量** | 1000 万+ 供稿/日 + 直播截帧 + 短视频，总量可能达 3000-5000 万/日 |
| **并发审核员** | 100 人同时在线，峰值可能 200+ |
| **直播实时性** | 截帧→AI→人审需在秒级完成，WebSocket 实时推送 |
| **部署环境** | 可能部署在公司内网或私有云，支持多租户隔离 |
| **多模态 AI** | 视觉 + NLP + ASR + 视频查重，需要灵活的路由和扩缩容 |
| **数据安全** | 审核内容涉及敏感信息，需租户级数据隔离 |

## 方案对比

### 方案 A：Go 微服务 + PostgreSQL + Redis + Kafka（推荐）

| 方面 | 说明 |
|------|------|
| **前端** | React 18 + TypeScript + Ant Design Pro（后台组件齐全） |
| **后端** | Go (Gin/Fiber) 微服务拆分，每个模块独立部署 |
| **数据库** | PostgreSQL（主存储）+ 分区表（审核记录按时间分区） |
| **缓存/队列** | Redis（会话/缓存）+ Kafka/RabbitMQ（审核任务队列） |
| **搜索** | Elasticsearch（审核记录全文检索、运营报表） |
| **对象存储** | MinIO（自建 S3 兼容） |
| **实时通信** | WebSocket（审核任务分配、直播电视墙刷新） |
| **优点** | 1. Go 高并发处理能力极强，适合千万级吞吐<br>2. 微服务拆分清晰，每个模块独立扩缩容<br>3. Kafka 削峰填谷，应对流量洪峰<br>4. Redis 做实时电视墙状态，毫秒级响应<br>5. ES 支持审核记录多维检索和报表<br>6. 部署简单（单二进制），资源占用低 |
| **缺点** | 1. Go 生态不如 Java/Python 丰富，ORM 需自封装<br>2. 微服务架构运维复杂度高（需要 K8s/服务发现）<br>3. 开发速度比单体慢，前期投入大 |
| **适合场景** | 千万级日处理量、多租户、实时性要求高 |

### 方案 B：Java Spring Boot + PostgreSQL + Redis + RabbitMQ

| 方面 | 说明 |
|------|------|
| **前端** | React 18 + TypeScript + Ant Design Pro |
| **后端** | Java 17 + Spring Boot 3 + Spring Cloud |
| **数据库** | PostgreSQL |
| **缓存/队列** | Redis + RabbitMQ |
| **优点** | 1. 企业级生态最成熟，权限/事务/缓存方案完善<br>2. Spring Security 开箱即用，RBAC 实现简单<br>3. 团队招聘容易，Java 开发者多 |
| **缺点** | 1. 启动慢、内存占用大（每个服务 500MB+）<br>2. 千万级吞吐需要更多实例，成本高<br>3. 微服务骨架重，前期搭建耗时 |
| **适合场景** | 团队有 Java 基础，重视企业级特性 |

### 方案 C：Node.js (NestJS) + PostgreSQL + Redis（折中方案）

| 方面 | 说明 |
|------|------|
| **前端** | React 18 + TypeScript + Ant Design Pro |
| **后端** | NestJS（Angular 风格的模块化框架） |
| **数据库** | PostgreSQL |
| **缓存/队列** | Redis + BullMQ（内置队列） |
| **优点** | 1. 前后端同语言（TS），开发效率高<br>2. NestJS 模块化架构清晰，天然支持微服务拆分<br>3. 比 Go 方案开发快，比 Java 方案轻量 |
| **缺点** | 1. Node.js 单线程，CPU 密集型任务（AI 调度）是瓶颈<br>2. 千万级吞吐需要更精细的水平扩展<br>3. 实时电视墙场景下，WebSocket 连接数大时内存增长快 |
| **适合场景** | 团队熟悉 TS，想快速上线再逐步优化 |

## 明确建议：方案 A（Go + PostgreSQL + Redis + Kafka）

**推荐理由：**

1. **吞吐量是首要约束**：日均千万级处理量，Go 的高并发和极低内存占用是核心优势。同样 1000 万 Q/日，Go 可能需要 5-10 个实例，Java 可能需要 20-30 个。
2. **直播实时性要求**：电视墙需要毫秒级刷新，Go 的 goroutine 模型天然适合 WebSocket 长连接，100 审核员 × 多路直播 = 数千并发连接，Go 轻松应对。
3. **微服务拆分清晰**：内容接入、AI 调度、审核工作台、租户管理各自独立，Go 微服务部署简单（单二进制）。
4. **Kafka 削峰**：千万级内容涌入时，Kafka 作为缓冲队列，AI 审核服务按需消费，不会被流量洪峰打垮。
5. **与架构设计文档一致**：原文档已推荐 Go + React，符合模拟 TikTok/Jacoco 这类互联网产品的技术调性。

**分阶段实施建议：**
- Phase 1（MVP）：先用单体 Go 应用 + PostgreSQL + Redis，跑通核心流程
- Phase 2：拆分微服务，引入 Kafka 队列
- Phase 3：引入 Elasticsearch 做搜索和报表，K8s 做编排
